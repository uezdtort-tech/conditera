# Conditera — предварительная инвентаризация существующей реализации

**Версия:** 0.1  
**Статус:** READ-ONLY / PRELIMINARY / NOT A PRODUCTION AUDIT  
**Объект:** кодовая база `main`, зафиксированная в ходе GitHub-проверки на commit `0aa70689397fc0d8fbb2260df4b377694de3a098`.  
**Назначение:** фиксировать проверяемые факты кода, архитектурные расхождения и вопросы для последующей проверки фактических PG15/PG18. Документ не утверждает, что просмотренный код совпадает с развёрнутыми кластерами или текущими runtime-конфигурациями.

## 1. Границы и метод

Проверены исходники и миграции в GitHub `main`: прямой PostgreSQL pool, API создания заказа и checkout, миграционный runner, Supabase compatibility SQL, миграции 0053/0054 и существующий документ консолидации БД.

Не проверялись через живое подключение:
- фактические схемы и данные production/dev PG15 и PG18;
- применённые migration ledgers и частично выполненные SQL;
- эффективные grants/RLS policies на каждом кластере;
- реальные Storage buckets, объекты и настройки внешнего Supabase Storage;
- переменные окружения production и маршруты Kong/PostgREST/GoTrue;
- фоновые задачи, очереди и фактическая доставка событий;
- содержимое volumes и резервные копии.

Поэтому все выводы ниже имеют уровень **CODE VERIFIED** или **NEEDS RUNTIME VERIFICATION**, но не **PRODUCTION VERIFIED**.

## 2. Два пути к данным — архитектурный риск №1

В `docs/DATABASE_CONSOLIDATION.md` зафиксирована следующая модель production Compose:
- Supabase JS Admin / GoTrue / PostgREST / Storage направляются через Supabase URL/Kong на PG15, БД `supabase`;
- прямой `getPool()` через `DATABASE_URL` направляется через PgBouncer на PG18, БД `conditera`;
- локальный REST shim использует прямой PG Pool;
- локальный Storage shim хранит файлы в `upload/storage`, а метаданные `storage.objects` — в PG18;
- production Supabase Storage использует отдельный Storage volume и PG15.

Исходник `src/lib/postgrest/pool.ts` подтверждает:
- `getPool()` читает `DATABASE_URL`;
- пустое значение или `file:` заменяется на встроенный локальный PostgreSQL по `CONDITERA_PG_PORT` (по умолчанию 54329);
- пул создаётся отдельно от Supabase Admin client.

**Риск:** один пользовательский сценарий может читать и писать разные логические данные через два подключения. Изменение только `DATABASE_URL` или только Supabase URL не объединяет источники истины. До проектирования PG17 нужно построить карту каждой операции и каждого API до фактического кластера/БД.

**Обязательная проверка:** для всех production-переменных, Compose profiles, PgBouncer, Kong, GoTrue, PostgREST, Storage и runtime-процессов получить фактические адреса/версии/имена БД без вывода секретов.

## 3. Создание заказа — неатомарные последовательности

### 3.1. `src/app/api/orders/route.ts`

Проверенный код:
1. Создаёт запись в `orders` через `supabaseAdmin`.
2. После успешной вставки отправляет `order.created` в n8n и ops event log.
3. Затем отдельно вставляет `order_items`.
4. При ошибке вставки позиций логирует ошибку и явно оставляет созданный заказ без позиций.
5. Дальнейшие действия (включая списание бонусов/компенсацию промокода) идут после этого участка.

**Подтверждённый дефект целостности потока:** событие `order.created` может быть опубликовано до успешной фиксации состава заказа; при ошибке `order_items` заказ остаётся без позиций. Это не атомарная операция.

### 3.2. `src/app/api/checkout/route.ts`

Проверенный код:
1. Создаёт `orders`.
2. Отдельно вставляет `order_items`.
3. При ошибке пытается удалить созданный заказ.
4. Результат удаления не проверяется и ошибка удаления не переводит поток в отдельное состояние восстановления.
5. Дальнейшее создание платёжной записи идёт отдельной операцией.

**Подтверждённый риск:** компенсирующее удаление может не выполниться/выполниться частично, но код всё равно возвращает общий 500. Фактическое состояние после ошибки не гарантировано этим кодом.

### 3.3. Целевое требование

Для обоих входных путей требуется единый доменный use case с атомарной границей (транзакционный RPC/серверная транзакция в одном источнике истины) либо явно спроектированная saga с идемпотентностью, outbox, компенсирующими действиями и reconciliation. Событие `order.created` должно означать, что обязательный состав заказа зафиксирован. Существующие два API нельзя объявлять эквивалентными без сравнения правил расчёта, бонусов, промокодов, налоговых снимков, доставки и оплаты.

До выбора решения нужно сопоставить:
- `ORD-001`–`ORD-010`;
- `FIN-001`–`FIN-011`;
- `NFR-003`, `NFR-005`, `NFR-006`;
- `SUP-005`, `FRD-005`.

## 4. Миграционный runner

В `supabase/init-scripts/01-apply-migrations.sh` подтверждено:
- используется собственная таблица `public.schema_migrations(filename, applied_at)`;
- файлы применяются в лексикографическом порядке;
- `psql -v ON_ERROR_STOP=1` останавливается на первой SQL-ошибке;
- migration ledger записывается после успешного выполнения файла;
- весь SQL-файл не обёрнут runner'ом в общую транзакцию;
- скрипт прямо предупреждает, что ошибка может оставить схему в частично применённом состоянии;
- миграция 0026 откладывается, пока не созданы `storage.buckets` и `storage.objects`;
- ledger проекта отличается от системного `supabase_migrations.schema_migrations`.

**Риск:** ledger отражает успешность файла только с точки зрения runner'а, но при ошибке внутри файла отдельные statements могли уже примениться. Повторный запуск не гарантирует безопасное восстановление для неидемпотентного SQL.

**Нужная проверка:** на каждом фактическом кластере собрать список файлов, ledger, checksum/версию файла и наличие каждого ожидаемого объекта. Сопоставить реальное состояние схемы с ledger; не исправлять расхождения автоматическим повторным прогоном.

### 4.1. Разрыв миграций CMS между main и PR #47

Сопоставление точных путей в `main` с изменёнными файлами PR #47 подтвердило:
- `supabase/migrations/0065_cms_home_blocks.sql` отсутствует в `main`, но присутствует в PR #47;
- `supabase/migrations/0068_cms_design_warm_defaults.sql` отсутствует в `main`, но присутствует в PR #47;
- `supabase/migrations/0069_cms_atomic_home_reorder.sql` отсутствует в `main`, но присутствует в PR #47;
- PR #47 также содержит последующие CMS-миграции 0070–0073; их состав виден в списке файлов PR.

Проверено содержимое трёх миграций в известном commit PR #47:
- 0065 создаёт `public.cms_home_blocks`, индексы, RLS, публичное чтение активных блоков и административное управление через роли ADMIN/SUPER_ADMIN/COPYWRITER;

**Следствие:** migration chain в main не содержит необходимого основания для CMS-функций, добавленных PR #47. Проверка CI на временной/PR-ветке не доказывает, что текущая main-схема или реальная БД уже имеет эти объекты. Не запускать эти файлы вручную и не переносить их отдельно от согласованного PR/cutover-процесса.

## 5. RLS и grants — зоны обязательной проверки

### 5.1. Миграция 0053

В коде явно создаются политики `FOR SELECT TO authenticated USING (true)` для:
- `domain_events`;
- `ops_tasks`;
- `purchase_drafts`;
- `purchase_draft_items`;
- `recipe_ingredients`.

Для `purchase_drafts` при этом существует `owner_id`, но проверенная SELECT policy не ограничивает выборку владельцем.

### 5.2. Миграция 0054

В коде явно создаются политики `FOR SELECT TO authenticated USING (true)` для:
- `confectioner_capacity`;
- `capacity_reservations`;
- `order_production`;
- `order_production_checklist`;
- `order_media`.

### 5.3. Что можно и нельзя заключить

**CODE VERIFIED:** в указанных миграциях присутствуют широкие permissive SELECT policies для роли authenticated.

**НЕ ДОКАЗАНО:** что эти таблицы доступны любому пользователю в фактической среде, поскольку нужно проверить эффективные grants, все policies (permissive OR / restrictive AND), владельцев таблиц, BYPASSRLS, роли подключения, API-обходы и фактическую применённую схему отдельно в PG15 и PG18.

Тем не менее это P0-зона проверки. Особенно чувствительны `domain_events.payload`, закупочные черновики, ингредиенты рецептур, назначения/capacity и `order_media`. До выяснения нельзя считать изоляцию tenant/org обеспеченной.

## 6. Фотофиксация заказа и Storage

### 6.1. Что уже существует в коде

Миграция `0054_order_lifecycle_capacity.sql` создаёт `public.order_media` с:
- `order_id`, `kind`, `media_type`;
- `storage_path`, `original_filename`, `mime_type`, `file_size`, `width`, `height`;
- `uploaded_by`, `uploaded_at`, `status`.

Комментарий миграции описывает локальный путь вида `storage/orders/<orderId>/published/photos/<uuid>.<ext>` и называет это внутренним QC-артефактом. Это не подтверждает использование приватного Supabase Storage bucket.

В `supabase/compat/0000_supabase_compat.sql` создаётся публичный bucket `media`; там же выдаются grants на `storage.buckets` и `storage.objects` для authenticated, а SELECT на buckets/objects — для anon. Реальный доступ к объектам всё равно зависит от всех действующих RLS policies и Storage API.

### 6.2. Расхождение с целевой моделью

Целевая модель требует приватное хранение order evidence, метаданные/связи в PostgreSQL, контроль доступа по заказу/позиции/роли и жизненный цикл загрузки/связи. Существующая миграция 0054 описывает локальный filesystem path и широкую SELECT policy на метаданные.

**Вывод:** `order_media` — существующий кандидат на переиспользование/эволюцию, но не доказательство готовой реализации целевого evidence flow. Не создавать вторую таблицу и не менять upload routes до полного аудита всех путей записи/чтения/удаления, Storage policies и защищённых файлов.

### 6.3. Фактические API и права на фото заказа

Проверены:
- `POST /api/orders/[id]/media`;
- `GET /api/orders/[id]/media`;
- `GET /api/order-media/[mediaId]`;
- `src/lib/ops/order-media.ts`;
- `src/lib/ops/order-access.ts`;
- `src/lib/role-guards.ts`;
- E2E-скрипт `scripts/verify/order-lifecycle-verify.mjs`.

Подтверждено:
- upload использует `getUserFromRequest` и `canOperateOrder`: назначенный кондитер или ADMIN/SUPER_ADMIN;
- MIME проверяется по magic bytes, поддерживаются JPEG/PNG/WebP, есть ограничение размера и UUID-имя;
- файл пишется в локальный filesystem, затем метаданные — в PG через `getPool()`;
- если вставка метаданных падает, код пытается удалить файл;
- E2E-скрипт проверяет сценарий «READY без фото → 422», загрузку фото и последующий READY;
- `GET /api/orders/[id]/media` также использует `canOperateOrder`, поэтому покупатель не может получить список evidence через этот endpoint, хотя целевая модель предусматривает просмотр фото своего заказа;
- `GET /api/order-media/[mediaId]` разрешает доступ владельцу заказа и указанному confectioner_id, а также любому пользователю с глобальной активной ролью ADMIN/SUPER_ADMIN/SUPPORT/COURIER через `hasAnyRole(userId, roles)`. Проверка не связывает роль COURIER с назначением на конкретную доставку и не связывает SUPPORT с конкретным обращением/эскалацией.

**P0 несоответствие целевой модели доступа:** staff-role check является глобальным по user_id, а не scoped к заказу/доставке/case. Это потенциально открывает фото любого заказа любому активному аккаунту с ролью SUPPORT или COURIER. Перед выводом о фактической экспозиции нужно проверить, кто может назначать эти роли, реальные аккаунты и внешние защитные слои; но серверный маршрут сам не проверяет связь курьера с доставкой. Нужен негативный тест «курьер A не может получить фото заказа, назначенного курьеру B» и аналогичная проверка support scope.

**P1/P0 race condition:** лимит пяти ready-фото проверяется запросом count до записи файла и метаданных, без общей транзакции/блокировки заказа. Два параллельных запроса при текущем count=4 могут оба пройти проверку и создать шестое фото. Нужен конкурентный тест и атомарный лимит на серверной стороне.

**P1 частичный отказ:** после успешного сохранения файла и строки `order_media` маршрут отдельно вызывает `setStageDone` и `recordEvent`. Если один из этих вызовов упадёт, клиент получит 500, хотя фото уже сохранено; повтор запроса может создать дубликат. Требуются идемпотентность и outbox/reconciliation для события и чеклиста.

Эти выводы основаны на просмотре кода. Они не доказывают, что существующий E2E проходит на текущем окружении или что реальная файловая система/PG18 синхронизированы.

## 7. Прочие факты для дальнейшей сверки

- Compatibility SQL создаёт stub-таблицы `storage.buckets` и `storage.objects`; это не следует путать с полным внешним Supabase Storage API.
- Compatibility SQL включает публичный `media` bucket, используемый как минимум CMS-путём; не следует автоматически помещать туда заказные доказательства.
- В `0053` доменные события описаны как append-only, но фактические права UPDATE/DELETE и доступ к payload нужно проверить отдельно.
- В `0054` поле `ready_photo_required` по умолчанию `false`; бизнес-правило обязательности фото не следует считать универсально включённым.
- Два API создания заказа имеют разные детали реализации и последовательности действий; их нельзя считать одним процессом только потому, что оба пишут `orders` и `order_items`.

### 7.1. Escrow release — недостаточный бизнес-гейт

Проверены `src/app/api/cron/escrow-release/route.ts` и `supabase/migrations/0037_payout_linkage.sql`.

В cron-запросе выбираются заказы:
- `payment_status = escrow`;
- `escrow_released_at IS NULL`;
- `status != CANCELLED`;
- `created_at < now() - 24h`.

В выборке нет условия `DELIVERED` или `COMPLETED`; время 24 часа считается от `created_at`, а не от `paid_at`/момента перехода в escrow. RPC `release_escrow_order` в 0037 атомарно выполняет claim и начисление, но проверяет только `payment_status='escrow'` и `escrow_released_at IS NULL`; бизнес-статус заказа не проверяется.

**Подтверждённое несоответствие кода целевой модели:** атомарность финансовой операции реализована, но атомарность не делает корректным её бизнес-условие. При текущем коде неотменённый заказ в PENDING/CONFIRMED/PREPARING/READY/IN_DELIVERY потенциально может попасть под release по возрасту создания. Дополнительно заказ, оплаченный спустя более 24 часов после создания, может попасть в выборку практически сразу после перехода в escrow.

Нельзя исправлять условие до согласования коммерческой политики: когда именно средства становятся доступными изготовителю, какие исключения предусмотрены для самовывоза, B2B, выездных услуг, частичной приёмки и претензий. Требуется новая модель escrow eligibility и тесты на каждый статус/временную границу.

### 7.2. Доступ к полному заказу и доставке

В `src/app/api/orders/[id]/route.ts` GET загружает `items:order_items(*)`, `payment:payments(*)`, `delivery:deliveries(*)`. Доступ разрешается владельцу, назначенному confectioner или любому пользователю с глобальной ролью ADMIN/SUPER_ADMIN/SUPPORT/COURIER. Для SUPPORT/COURIER в этом GET нет проверки связи с конкретным support case или назначенной доставкой.

В том же файле PATCH переходы для COURIER дополнительно проверяют запись `deliveries(order_id, courier_id)`; следовательно, проверка назначения есть для изменения статуса, но не для чтения полного payload через GET.

**P0 несоответствие:** read-access шире, чем write-access и целевая модель минимальных полномочий. Курьеру не должны автоматически раскрываться все платёжные данные и полная история любого заказа только из-за глобальной роли. Доступ SUPPORT должен быть связан с обращением/эскалацией, а доступ COURIER — с конкретным назначением и минимальным набором данных.

### 7.3. Подтверждение передачи заказа

В `src/app/api/orders/[id]/handoff/route.ts` поле `body.code` принимается, но не валидируется и не участвует в разрешении перехода; в event payload сохраняется только признак `provided`. Исполнитель берётся из свободного текстового поля или имени пользователя. Роут разрешает действие назначенному кондитеру/администратору и переводит заказ в IN_DELIVERY либо DELIVERED при самовывозе.

В `PATCH /api/orders/[id]` курьерский переход проверяет назначение в `deliveries`, но сам по себе не заменяет доказательство физической передачи.

**Несоответствие целевой модели:** нет подтверждённого одноразового, order-bound и courier-bound proof of handoff в этом endpoint. Нужны правила для QR/OTP/подписи/фото/альтернативной процедуры, срок действия, одноразовость, защита от replay, отмена/переназначение курьера и аудит. До этого нельзя считать поле `code` доказательством передачи.

### 7.4. Курьерский dashboard и достоверность финансовых показателей

В `src/app/api/courier/dashboard/route.ts` при ошибке БД возвращается `STUB_DATA` даже в production (внутренний catch DB error не проверяет NODE_ENV). В реальном ответе:
- earningsToday/earningsMonth вычисляются суммой `orders.delivery_cost`, а не подтверждёнными начислениями/выплатами курьера;
- если нет профиля/рейтинга, подставляется 5.0;
- история также отдаёт rating=5 как заглушку;
- расстояние всегда `—`.

**Риск:** интерфейс может показывать демонстрационные или не являющиеся заработком курьера суммы как реальные финансовые показатели. Для финансового кабинета источник должен быть ledger/начислениями курьеру, а недоступность БД должна возвращать явную ошибку/недоступность, не demo-данные.

## 8. Следующий план read-only инвентаризации

1. Получить фактическую топологию и runtime-конфигурацию PG15/PG18, без раскрытия секретов.

### 7.5. Платёжный webhook, отмена и возврат — разрыв финансовой машины состояний

Проверены полные реализации:
- `src/app/api/payment/webhook/route.ts`;
- `src/app/api/payment/create/route.ts`;
- `src/app/api/payment/refund/route.ts`;
- `src/app/api/orders/[id]/cancel/route.ts`;
- `src/app/api/cron/escrow-release/route.ts`;
- `src/lib/yookassa.ts`;
- `supabase/migrations/0037_payout_linkage.sql`;
- `supabase/migrations/0039_release_readiness.sql`;
- `supabase/migrations/0041_refund_idempotency.sql`.

#### Что сделано правильно (CODE VERIFIED)

- В production webhook проверяет IP по allowlist YooKassa; дополнительно для платёжных событий запрашивает статус платежа у провайдера, а для `refund.succeeded` — сам объект возврата.
- Платёж ищется по `yookassa_payment_id`; для возврата используется `object.payment_id`.
- Сумма платежа сверяется с суммой в БД в копейках.
- Повторные `refund.succeeded` дедуплицируются по refund ID через `apply_yookassa_refund` (0039); частичные возвраты суммируются атомарно.
- RPC `release_escrow_order` (0037) атомарно связывает claim заказа и увеличение баланса кондитера в одной транзакции.
- API возврата отделяет заявку покупателя от исполнения: покупатель создаёт `requested`, исполнение разрешено ADMIN/SUPER_ADMIN.
- `refunds` имеет уникальность Idempotency-Key в рамках инициатора и индекс одной открытой заявки на платёж (0041).

Эти механизмы снижают риск повторных операций, но не обеспечивают целостность всей бизнес-операции между несколькими запросами/таблицами/провайдером.

#### P0 — гонка отмены с release escrow

`POST /api/orders/[id]/cancel` сначала меняет `orders.status` на `CANCELLED`, но не меняет `payment_status` в этой же операции. Затем отдельными запросами пишет историю и вызывает возврат у провайдера.

Cron выбирает кандидатов по `status != CANCELLED`, но RPC `release_escrow_order` повторно проверяет только:
- `payment_status = escrow`;
- `escrow_released_at IS NULL`.

В RPC нет проверки `orders.status`. Если cron успел выбрать заказ до отмены, а RPC вызван после того, как отмена уже поставила `status=CANCELLED`, RPC всё ещё может перевести деньги в `released` и начислить баланс. Проверка статуса только в SELECT cron не защищает от этой гонки.

**Статус:** CODE VERIFIED. Требуется конкурентный тест cancel × escrow-release и исправление единой атомарной машиной состояний; не ограничиваться дополнительным фильтром в cron.

#### P0 — поздний payment.succeeded может вернуть отменённый заказ в escrow

В webhook для `payment.succeeded` после проверки суммы выполняется:
- обновление `payments.status`;
- отдельный CAS на `orders.payment_status='escrow'`, условие только `id=orderId AND payment_status != 'escrow'`.

В CAS нет условия `orders.status != 'CANCELLED'` и нет проверки текущей попытки оплаты. Поэтому позднее подтверждение оплаты может установить `payment_status='escrow'` уже отменённому заказу. При этом cron не возьмёт такой заказ из-за `status=CANCELLED`; деньги могут остаться в несогласованном состоянии без автоматического возврата.

**Статус:** CODE VERIFIED. Нужны тесты: cancel до webhook; webhook до cancel; два платежных поколения; поздний webhook старой попытки после новой попытки. Переход должен проверять допустимость заказа и конкретной payment attempt атомарно.

#### P0 — endpoint отмены считает возврат завершённым по факту принятия запроса провайдером

В `orders/[id]/cancel/route.ts` после `refundPayment(...)` при `result.success` немедленно:
- ставит `payments.status='refunded'`;
- ставит `orders.payment_status='refunded'`.

Но успешный HTTP-ответ YooKassa на создание возврата не равен подтверждённому `refund.succeeded`. В том же проекте `/api/payment/refund` корректно переводит заявку в `processing`, а окончательное состояние оставляет webhook после проверки объекта возврата.

Кроме того, путь отмены не создаёт запись в `refunds`, не сохраняет `yookassa_refund_id` и не передаёт собственный Idempotency-Key. Поэтому теряется единая история возврата и связь с заявкой/претензией; повторная обработка и сверка сложнее. В `refundPayment` без ключа используется один детерминированный ключ на payment ID, что может сделать повторный полный refund-запрос идемпотентным, но не заменяет запись операции и reconciliation.

**Статус:** CODE VERIFIED. Нужно свести отмену и ручной возврат к одному refund use case и одному журналу операций; `refunded` выставлять только после подтверждённого webhook/сверки с провайдером.

#### P1 — резерв частичного возврата снимается отдельным read-then-write

В `/api/payment/refund` админский путь вызывает RPC `reserve_refund`, затем создаёт строку `refunds`, вызывает YooKassa, а после принятия запроса провайдером сбрасывает `payments.refund_amount` обратно в ранее прочитанное `alreadyRefunded`, ожидая финальный webhook.

Код сам комментирует, что до прихода webhook есть окно, когда резерв не виден следующему запросу. Более того, сброс выполняется абсолютным значением, полученным до внешнего вызова. При двух параллельных частичных возвратах или при неудачном/задержавшемся запросе один процесс может записать устаревшее значение поверх резерва другого процесса. Это требует отдельного конкурентного теста; текущий временный резерв в `payments.refund_amount` смешивает подтверждённую сумму и незавершённые суммы.

**Статус:** CODE VERIFIED как последовательность операций; конкретная потеря резерва — NEEDS CONCURRENCY TEST. Целевое решение — отдельные refund intents/reservations и ledger, где requested/processing/succeeded/failed учитываются раздельно, а доступный остаток вычисляется атомарно.

#### P1 — статус payment row обновляется без проверки результата

В webhook результат UPDATE `payments.status` после проверки суммы не проверяется на ошибку. Обработчик может продолжить и перевести заказ в escrow, даже если статус строки конкретного платежа не обновился. Аналогично ряд операций записи уведомлений/событий намеренно fail-safe и не блокирует ответ; для финансовых фактов нужна отдельная гарантированная очередь/outbox и сверка, а не только логирование.

**Статус:** CODE VERIFIED. Нужны проверка результата всех финансовых записей и reconciliation по provider payment ID.

#### P1 — payment.canceled обновляет бизнес-статус заказа без атомарного guard

Webhook проверяет ранее загруженный snapshot заказа, затем отдельным UPDATE устанавливает `payment_status='cancelled', status='CANCELLED'` по одному только `id`. Между чтением и UPDATE состояние могло измениться; условие UPDATE не защищает от перезаписи более нового состояния заказа. Особенно важно проверить сценарий старой/повторной попытки оплаты при наличии нового платежа.

**Статус:** CODE VERIFIED. Нужен CAS по ожидаемому статусу заказа и payment attempt, а также тесты с переставленным порядком webhook-событий.

#### P1 — событие refund.succeeded может подтвердить платёж, но не обновить refund request

Webhook сначала применяет сумму через RPC, затем пытается обновить `refunds` по `yookassa_refund_id`. Ошибка UPDATE не проверяется: Supabase возвращает ошибку в объекте результата, а не обязательно бросает исключение, поэтому текущий `try/catch` её не гарантирует. Путь отмены вообще не создаёт refund row. Возможен финансово подтверждённый возврат без корректного статуса связанной заявки.

**Статус:** CODE VERIFIED. Нужна сверка всех provider refund IDs с локальными refund intents и отдельная очередь восстановления.

#### P1 — события и уведомления не имеют общей гарантии с финансовым переходом

Webhook выполняет несколько внешних действий после CAS: n8n, ops event, Telegram, Метрика, email, chat, бонусы и уведомления. Большинство ошибок только логируются; сам webhook после этого отвечает 200. CAS не позволит повторному webhook повторить побочные действия, но если процесс упал после CAS и до конкретного действия, повторный webhook уже увидит escrow и пропустит side effects. Значит часть уведомлений/аналитики/бонусов может потеряться навсегда без независимого outbox/retry worker. Проверка бонуса через SELECT, затем award — отдельная последовательность; реальную защиту от гонки нужно подтвердить уникальным ограничением/атомарной функцией в БД.

**Статус:** CODE VERIFIED для crash window и отсутствия общей транзакции; NEEDS RUNTIME VERIFICATION для фактических уникальных ограничений и восстановления.

#### P2 — waiting_for_capture трактуется как escrow

Webhook обрабатывает `payment.waiting_for_capture` в том же блоке, что и `payment.succeeded`, и переводит заказ в escrow. При этом `createPayment` отправляет YooKassa `capture: true`, то есть обычный поток должен быть автоматическим списанием. Тем не менее код допускает состояние авторизации без подтверждённого capture как состояние полученных денег. Требуется зафиксировать инвариант: только подтверждённый `succeeded` может запускать escrow; `waiting_for_capture` должен оставаться отдельным промежуточным состоянием, если он вообще поддерживается.

**Статус:** CODE VERIFIED как объединение обработчиков; фактическая достижимость этого статуса в текущей конфигурации — NEEDS PROVIDER/SANDBOX TEST.

#### Приоритетные сценарии приёмки платёжного контура

1. Один `payment.succeeded` доставлен 1, 2 и 10 раз — ровно один финансовый переход и ровно один набор гарантированно доставленных side effects.
2. Два разных платежных ID на один заказ; старый `payment.canceled` приходит после нового `payment.succeeded`.
3. `payment.succeeded` приходит после `orders.status=CANCELLED`.
4. Cancel и escrow cron стартуют одновременно; отдельно — cron выбрал заказ, cancel завершился, затем RPC release вызван.
5. Полный возврат: провайдер принял запрос, но webhook задержан/не пришёл; состояние не должно ложно показывать завершённый возврат.
6. Два параллельных частичных возврата, один провайдерский timeout с неизвестным результатом, повтор запроса и переставленные webhook.
7. Дублирующий `refund.succeeded` с тем же refund ID; два разных refund ID для одного платежа; сумма ровно равна и чуть превышает остаток.
8. Ошибка каждого DB UPDATE/RPC после ответа провайдера; восстановление через reconciliation.
9. Crash после финансового CAS, но до бонусов/уведомлений/n8n/email — outbox должен восстановить работу.
10. `waiting_for_capture` не может открыть выплату кондитеру.

Ни один из этих сценариев не объявляется пройденным по факту наличия E2E-файла или миграции. Нужны реальные тесты на актуальной схеме и отдельные sandbox/provider tests.



### 7.6. Доставка событий в n8n и внутренний event log — нет гарантии доставки

Проверены:
- `src/lib/n8n.ts`;
- `src/lib/ops/events.ts`;
- точки вызова из `src/app/api/payment/webhook/route.ts`, `src/app/api/checkout/route.ts` и `src/app/api/orders/route.ts`;
- `src/lib/postgrest/pool.ts`.

**CODE VERIFIED — HTTP-ошибки n8n не распознаются.** `emitEvent` вызывает `fetch(...)`, но не проверяет `response.ok` или HTTP status. При ответе n8n 400/401/404/500 сетевой запрос считается успешно завершившимся: исключения нет, dead-letter не создаётся. Dead-letter вызывается только при исключении/таймауте сети. Следовательно, событие может быть фактически отвергнуто n8n, но приложение не зафиксирует недоставку.

**CODE VERIFIED — отсутствие URL означает безусловную потерю события.** Если `N8N_WEBHOOK_BASE_URL` и `N8N_BASE_URL` не заданы, функция делает no-op и пишет информационное сообщение максимум один раз на процесс. В очередь или dead-letter событие не попадает.

**CODE VERIFIED — dead-letter сам не гарантирован.** При сетевой ошибке запись в `audit_log` выполняется best-effort; если она не удалась, код прямо пишет `event lost`. В проверенном модуле нет durable retry queue, lease/claim, backoff, повторной доставки и механизма гарантированного закрытия dead-letter после успешной обработки.

**CODE VERIFIED — domain event log и основная операция не атомарны.** `recordEvent` пишет в `public.domain_events` через `getPool()` (прямой `DATABASE_URL`), тогда как заказ и платёжные строки в рассмотренных маршрутах пишутся через `supabaseAdmin`. Это отдельные вызовы и, согласно текущей схеме подключений, потенциально разные кластеры/БД. Ошибка записи события поглощается внутри `recordEvent`; вызывающий маршрут не получает результат и не может откатить/поставить операцию на повтор.

**Важно:** уникальный `dedup_key` в миграции 0060 защищает от повторной вставки одинакового доменного события, но сам по себе не обеспечивает доставку, повторную обработку или атомарность с заказом.

**Риск для бизнеса:** платёж/заказ/возврат может успешно измениться, а timeline, аналитика, n8n-автоматизация или интеграционное действие — не выполниться; при HTTP 500 от n8n это может остаться незамеченным. И наоборот, если событие отправлено до полной фиксации заказа (как в раннем потоке `/api/orders`), автоматизация может увидеть неполный объект.

**Целевое решение:** transactional outbox в том же источнике истины, что и агрегат операции; уникальный event ID; durable delivery attempts; проверка HTTP-кодов и схемы ответа; retry с backoff; dead-letter с повторным запуском; consumer idempotency; мониторинг lag/failed events. До выбора PG17 нельзя оставлять outbox на неясной границе PG15/PG18.

**Статус:** CODE VERIFIED. Runtime-доставка, текущие n8n workflows, конфигурация webhook URL и содержимое dead-letter в фактической среде — NEEDS RUNTIME VERIFICATION.

### 7.7. Выплаты кондитерам — разделение резерва и подтверждения выплаты

Проверены `src/app/api/payouts/request/route.ts` и `src/app/api/admin/payouts/route.ts`.

**Что подтверждено в коде:**
- `/api/payouts/request` выбирает только заказы со статусом `payment_status='released'`, `escrow_released_at IS NOT NULL`, бизнес-статусом DELIVERED/COMPLETED и без прежней выплаты/резерва.
- Используется общая `computeOrderPayout`, та же формула, что и в escrow cron.
- Требуется полная сумма доступного батча; частичные выплаты прямо запрещены до полноценного ledger.
- Заявка создаётся как `pending`; баланс резервируется RPC `deduct_confectioner_balance`; заказы резервируются CAS по `payout_request_id`.
- При конфликте резерва есть попытка компенсировать списание и снять только собственные резервы.
- `/api/admin/payouts` разделяет approve/reject/complete; переходы статуса используют CAS.
- `complete` проверяет состав `metadata.orders`, помечает только заказы своей заявки, проверяет полноту батча и только затем переводит заявку в `paid`.
- `reject` возвращает резерв только заявкам с непустым `metadata.orders`, не печатая деньги для заявок, которые не резервировали баланс.

**P1 — два конкурирующих API создания payout request.** `POST /api/payouts/request` создаёт финансово обеспеченную заявку с резервом и связью заказов. Но `POST /api/admin/payouts` также доступен аутентифицированному пользователю с профилем кондитера и создаёт `pending` заявку произвольной суммы до 10 млн ₽ без проверки доступного баланса, без списания резерва и без `metadata.orders`. Комментарий к PATCH подтверждает, что такая заявка не может быть завершена как выплаченная; reject также не возвращает баланс, так как резерва не было. Это отдельный нефинансовый/неисполняемый тип заявки, но он использует ту же таблицу и тот же пользовательский список выплат.

**Риск:** два endpoint создают внешне похожие `pending` payout requests с разной экономической семантикой. UI/оператор может принять необеспеченную заявку за полноценную заявку на вывод. Необходимо либо удалить/закрыть альтернативный POST после проверки всех клиентов, либо явно разделить типы заявок и состояния в модели; нельзя просто включить резервирование в этот POST без транзакционного пересмотра.

**P1 — complete подтверждает ручное действие администратора, а не факт банковского перевода.** В проверенном PATCH `complete` нет вызова банка/платёжного провайдера и нет обязательного внешнего transaction/reference ID или документа подтверждения. Маршрут ставит `status='paid'` и `payout_transferred_at` после административного действия. Это допустимо только если продукт сознательно определяет операцию как ручную выплату вне платформы и хранит достаточные доказательства/аудит. Для автоматических выплат нужен отдельный provider state machine и reconciliation. Решение — OPEN POLICY DECISION, а не доказанный дефект.

**P1 — компенсации могут завершиться частично.** В `/api/payouts/request` при ошибке резервирования заказа код сначала переводит заявку в rejected, затем отдельно снимает резервы заказов и отдельно возвращает баланс RPC. Ошибки снятия/возврата только логируются; API возвращает 409, хотя финансовая компенсация могла не завершиться. Аналогичные предупреждения возвращаются в admin reject. Это не атомарная saga с гарантированной повторной компенсацией: требуется durable compensation task/reconciliation и операторский список незакрытых компенсаций.

**Статус:** CODE VERIFIED для разных семантик двух POST и отдельных компенсационных шагов; NEEDS RUNTIME VERIFICATION для реальных ограничений/триггеров и состояния существующих payout rows.

#### Приоритетные сценарии приёмки событий и выплат

1. n8n отвечает 200, 202, 400, 401, 404, 429, 500; каждый результат должен иметь правильную судьбу и метрику.
2. n8n недоступен, URL отсутствует, таймаут; событие сохраняется для повторной доставки.
3. Приложение падает после фиксации заказа/платежа, но до n8n; outbox worker доставляет после рестарта.
4. Два одинаковых event ID и два разных event ID одного заказа; consumer не дублирует денежные side effects.
5. Ошибка записи domain event при успешном создании заказа; reconciliation обнаруживает пропуск.
6. Создание payout request через оба POST; UI и админка не смешивают обеспеченную и необеспеченную заявку.
7. Ошибка возврата резерва баланса после reject; операция остаётся видимой как требующая восстановления, не считается завершённой.
8. Ошибка снятия payout_reserved_at при reject; повтор восстановления не затрагивает резерв другой заявки.
9. Администратор завершил выплату, но внешний перевод не состоялся/не подтверждён; модель не должна выдавать ручную отметку за подтверждённый банковский факт, если выбран автоматический режим.



### 7.8. Регистрация и RBAC — самоназначение роли с правами публикации CMS

Проверены:
- `src/app/api/auth/register/route.ts`;
- `src/app/api/auth/login/route.ts`;
- `src/lib/auth.ts`;
- `src/lib/supabase/auth.ts`;
- `src/app/api/cms/pages/route.ts`;
- `src/app/api/cms/pages/[slug]/route.ts`;
- `src/app/api/cms/banners/route.ts`;
- `src/lib/role-guards.ts`.

#### P0 — публичная саморегистрация выдаёт COPYWRITER, а COPYWRITER может публиковать CMS

В `POST /api/auth/register` сервер принимает поле `role` из тела запроса и включает `COPYWRITER` в `ALLOWED_SELF_REGISTER_ROLES`. Затем он делает UPSERT в `user_roles` с `is_active=true` и `assigned_by=userId`. Это не только UI-выбор: проверка находится на сервере, поэтому её можно вызвать напрямую без формы.

Проверенные полномочия COPYWRITER:
- `POST /api/cms/pages` разрешён ADMIN/SUPER_ADMIN/COPYWRITER; поле `status` принимается из тела запроса, в том числе `published`;
- `PATCH /api/cms/pages/[slug]` разрешён тем же ролям и позволяет менять `content` и `status` на `published`;
- `POST /api/cms/banners` также разрешён ADMIN/SUPER_ADMIN/COPYWRITER; баннер по умолчанию создаётся активным (`is_active=true`).

Следовательно, любой посетитель может зарегистрировать аккаунт с `role=COPYWRITER`, получить активную роль и полномочия создавать/публиковать CMS-страницы и баннеры. Отдельного подтверждения администратором или проверки доверенного приглашения в этом пути нет.

**Статус:** CODE VERIFIED, P0. Это прямой privilege escalation из публичной регистрации в привилегию управления публичным контентом. Нельзя считать COPYWRITER безопасной ролью саморегистрации только потому, что это не ADMIN. Роль должна назначаться администратором/по одноразовому приглашению; существующие аккаунты с этой ролью нужно отдельно проверить по фактической БД. До исправления нельзя открывать публичную регистрацию в production.

**Обязательные тесты:** анонимная регистрация с `CUSTOMER`, `COPYWRITER`, `ADMIN`, `SUPER_ADMIN`; после входа проверить фактические активные роли и попытки POST/PATCH CMS pages, публикации и создания активного banner. COPYWRITER из саморегистрации должен получать отказ, а не активную привилегию.

#### P1 — email-confirmation фактически обходится при первом входе

В регистрации `supabaseAdmin.auth.admin.createUser` вызывается с `email_confirm: false`, что выглядит как требование подтверждения email. Однако `POST /api/auth/login` сначала проверяет пароль по `profiles.password_hash`. Если последующий GoTrue `signInWithPassword` отвечает `Email not confirmed`, код вызывает `supabaseAdmin.auth.admin.updateUserById(user.id, { email_confirm: true })` и повторяет вход. App-JWT выдаётся дальше и без успешного подтверждения письмом.

Фронтенд `AuthModal` после успешной регистрации сразу вызывает `/api/auth/login`, то есть использует именно этот путь. В проверенном потоке нет доказательства владения email через одноразовую ссылку до снятия ограничения.

**Риск:** пользователь может зарегистрировать чужой email, подтвердить его не через почтовый канал, а знанием собственного только что заданного пароля; адрес будет занят и связан с его профилем. Это подрывает идентификацию, восстановление доступа и доверие к email-адресу.

**Статус:** CODE VERIFIED для обхода email-confirmation в коде; продуктовая политика — NEEDS POLICY CONFIRMATION. Если email должен быть подтверждён до полноценной активации, нужно убрать auto-confirm из login, ввести pending/unverified состояние и ограничить операции до подтверждения. Если email confirmation сознательно не требуется, убрать противоречивые флаги/комментарии и явно определить альтернативный механизм верификации контакта.

#### P1 — несовпадающие условия юридических согласий password/OAuth

Обычная регистрация требует `consentPd=true`, `consentTerms=true` и `consentOffer=true`, а затем пишет три отдельных события согласия (ПД, условия, оферта). OAuth callback для нового аккаунта требует только cookie согласия ПД и пользовательского соглашения, создаёт только два события (ПД и terms). Cookie `oauth_consent_offer_*` очищается, но в проверенном OAuth flow не устанавливается и не проверяется.

**Статус:** CODE VERIFIED как различие потоков; юридическая достаточность — NEEDS LEGAL REVIEW. Требуется единая матрица согласий по типу аккаунта и каналу регистрации, версии документов, доказательства согласия и отказа. Нельзя автоматически считать маркетинговое согласие обязательным или включённым.

#### P1 — legacy email magic-link callback не соответствует единому session-cookie контракту

`src/lib/supabase/use-auth.ts` использует `emailRedirectTo: /auth/callback`. Но `src/app/auth/callback/route.ts` после `exchangeCodeForSession` вручную устанавливает cookies `sb-access-token` и `sb-refresh-token`, тогда как канонический `getUserFromRequest` распознаёт `cd_session`, Bearer и cookie вида `sb-<project>-auth-token`. Эти имена не совпадают. Кроме того, callback передаёт `returnTo` непосредственно в redirect без той же явной внутренней allowlist-проверки, которая есть в новом OAuth callback.

**Статус:** CODE VERIFIED для несовпадения имён cookie; фактическая работа email magic-link зависит от конфигурации браузерного Supabase клиента и требует E2E. Нужно либо перевести этот маршрут на единый `setSessionCookies`/канонический handoff, либо удалить/перенаправить устаревший путь после поиска всех потребителей. Отдельно проверить безопасную нормализацию `returnTo`.

#### P2 — ошибки проверки DaData при регистрации проглатываются

Для `accountType=legal` ошибка DaData обрабатывается как non-blocking warning и регистрация продолжается. Несовпадение данных при успешном ответе приводит к отказу, но недоступность провайдера/ошибка проверки не блокирует создание legal-профиля. После регистрации повторная проверка также best-effort.

**Статус:** CODE VERIFIED. Нужно явно различить `VERIFIED`, `REJECTED`, `PENDING_REVIEW` и `VERIFICATION_UNAVAILABLE`; юридический аккаунт не должен получать доступ к B2B/выплатам/закупкам только потому, что внешний реестр был недоступен. Текущие downstream gates проверить отдельно.

#### Приоритетные сценарии приёмки Auth/RBAC

1. Прямая регистрация через API с каждой ролью из self-register allowlist; сравнить фактические права, а не только ответ UI.
2. COPYWRITER: попытки создать опубликованную страницу, изменить чужую страницу, опубликовать баннер, изменить SEO и контент.
3. ADMIN/SUPER_ADMIN/MODERATOR/SUPPORT и другие staff роли — публичная регистрация должна быть невозможна.
4. Регистрация с email, к которому пользователь не имеет доступа; вход, подтверждение, сброс пароля и повторная регистрация тем же email.
5. OAuth новый пользователь: отдельно проверить consent PD, terms и offer; отказ от каждого; отсутствие обязательного согласия не должно обходиться.
6. Magic link: после callback проверить /api/auth/session, getUserFromRequest, SSR useAuth и все API, требующие cookie.
7. Отзыв роли/блокировка/soft-delete сразу после выдачи JWT; все маршруты должны применить изменение без ожидания истечения JWT.
8. DaData timeout/5xx/unknown: аккаунт остаётся в явно ограниченном состоянии до успешной проверки/ручного решения.



### 7.9. Заказ: параллельные машины статусов и обход обязательных гейтов

Проверены:
- `src/app/api/orders/[id]/route.ts` (PATCH и GET);
- `src/lib/ops/lifecycle.ts`;
- `src/lib/ops/order-access.ts`;
- `src/app/api/orders/[id]/ready/route.ts`;
- `src/app/api/orders/[id]/production/start/route.ts`;
- `src/app/api/orders/[id]/handoff/route.ts`;
- `src/app/api/orders/[id]/complete/route.ts`;
- `src/app/api/orders/[id]/assign/route.ts`;
- `supabase/migrations/0001_init.sql`;
- `scripts/db/setup.mjs`;
- клиенты `src/lib/use-dashboard-data.ts`, `src/lib/use-real-orders.ts` и E2E `scripts/verify/order-lifecycle-verify.mjs`.

#### P0 — старый PATCH остаётся активным и обходит lifecycle engine

`PATCH /api/orders/[id]` продолжает использоваться в dashboard-клиентах и проверяется E2E. Он реализует собственную таблицу `STATUS_TRANSITIONS`, самостоятельно читает заказ через `supabaseAdmin`, проверяет роли и затем без CAS обновляет `orders.status` только по `id`.

В отличие от `applyOrderTransition`, этот PATCH:
- не проверяет `payment_status` перед PENDING → CONFIRMED;
- переводит PREPARING → READY без чеклиста и ready-photo gate;
- допускает IN_DELIVERY → DELIVERED без отдельного handoff proof;
- допускает DELIVERED → REFUNDED по роли ADMIN/SUPER_ADMIN/INSPECTOR, но не вызывает платёжный refund use case, не меняет `payment_status`, не создаёт refund record и не проверяет фактическое поступление денег;
- не пишет `order_status_history`;
- не использует CAS по исходному статусу: конкурентный запрос может перезаписать состояние, прочитанное ранее;
- публикует только общий `order.status_changed`, не обеспечивая согласованность с полным набором событий и side effects lifecycle engine.

Новые endpoint'ы `/ready`, `/production/start`, `/handoff`, `/complete` используют `applyOrderTransition` и отдельные проверки. Но наличие этих endpoint'ов не защищает от обхода, пока старый PATCH доступен клиентам и API.

**P0 — особенно опасно:** `PATCH {status:"REFUNDED"}` является только изменением бизнес-статуса. Это может показать заказ «возвращённым» без реального возврата денег; `payment_status` останется прежним.

**Статус:** CODE VERIFIED. Нужен один публичный переходный API/доменный use case; старые клиенты должны быть переведены на него, а PATCH либо стать тонкой обёрткой над engine с теми же гейтами, либо запретить опасные переходы. REFUNDED должен быть результатом подтверждённой финансовой операции, а не самостоятельным статусным PATCH.

#### P0 — прямой PATCH может подтвердить неоплаченный заказ и обойти фото/QC

В старом PATCH нет условия `payment_confirmed_or_cash`, которое есть в lifecycle engine для PENDING → CONFIRMED. Также PREPARING → READY не вызывает `checkReadyGate`; обязательность чеклиста и фото проверяется только в отдельном POST `/ready`.

Следовательно, вызов PATCH напрямую может:
- подтвердить заказ, для которого платёж не подтверждён и способ оплаты не cash;
- поставить READY без завершения производственного чеклиста;
- поставить READY без фото готовности для категории, где `readyPhotoRequiredForCategory` требует фото.

Это не гипотетическая разница UI: серверный PATCH сам принимает эти переходы и не вызывает соответствующие проверки.

**Статус:** CODE VERIFIED, P0. Обязательные негативные тесты — прямой PATCH для unpaid order, незавершённого checklist и категории с обязательным фото; все должны быть отклонены.

#### P1 — бизнес-статус и история могут расходиться между двумя БД и двумя реализациями

`PATCH /api/orders/[id]` читает/пишет `orders` через `supabaseAdmin`; lifecycle engine, `loadOrderLite`, производство и связанные операции читают/пишут `orders` через `getPool()`. Согласно уже зафиксированной карте подключений, это потенциально PG15 и PG18 соответственно.

Даже если каждая реализация локально использует свои проверки, CAS/транзакция на PG18 не сериализует конкурентную запись, пришедшую через PG15. Фактическая синхронизация строк между этими кластерами не доказана.

**Статус:** CODE VERIFIED для двух разных writer paths; NEEDS RUNTIME VERIFICATION для реального расположения данных и репликации. До подтверждения единого источника истины нельзя считать lifecycle engine единственной машиной состояний.

#### P1 — регистрация не деактивирует CUSTOMER, автоматически добавленный триггером

`supabase/migrations/0001_init.sql` содержит `on_auth_user_created`, который вставляет активную роль CUSTOMER. `POST /api/auth/register` затем делает UPSERT выбранной роли, но не деактивирует CUSTOMER для ролей CONFECTIONER/COURIER/SUPPLIER и других. В отличие от этого, `scripts/db/setup.mjs` явно деактивирует CUSTOMER у пользователей с ролью не CUSTOMER.

В `POST /api/orders/[id]/complete`:
- клиент-владелец определяется отдельно;
- не-владелец может пройти предварительную проверку как назначенный кондитер через `canOperateOrder`;
- затем `actorRoles` передаются целиком в lifecycle engine;
- переход DELIVERED → COMPLETED разрешён роли CUSTOMER или ADMIN/SUPER_ADMIN.

Если зарегистрированный кондитер сохранил активную CUSTOMER из auth trigger, он может пройти роль-гейт как CUSTOMER на заказе, который ему назначен, хотя не является владельцем заказа. В самом `applyOrderTransition` проверка ownership для CUSTOMER отсутствует.

**Статус:** CODE VERIFIED для несовпадающей обработки ролей в register vs setup и для логики complete; наличие активных CUSTOMER у реальных кондитеров — NEEDS RUNTIME VERIFICATION. Нужен тест с пользователем CUSTOMER+CONFECTIONER, назначенным на чужой заказ: он не должен иметь право подтверждать получение/завершение от имени покупателя. Роль должна интерпретироваться как контекст конкретного действия, а не как простое наличие любой роли.

#### P1 — lifecycle engine заявляет SELECT FOR UPDATE, но фактический SELECT не блокирует строку

Комментарий `applyOrderTransition` утверждает `FOR UPDATE + CAS`, но фактический SQL `SELECT ... FROM public.orders WHERE id=$1 LIMIT 1` не содержит `FOR UPDATE`. CAS UPDATE по `status=from` защищает от двух конкурентных переходов внутри одной и той же БД и одной машины, но не от независимых writers на другом кластере/через другой API. Чеклист/QC читается до CAS и без блокировки заказа.

**Статус:** CODE VERIFIED для отсутствия FOR UPDATE. Само по себе отсутствие блокировки не доказывает двойной переход в рамках одного writer path из-за CAS; риск становится существенным при параллельном старом PATCH и PG15/PG18 split. Необходимо либо реально блокировать агрегат, либо доказать достаточность единой атомарной RPC и убрать конкурирующих писателей.

#### Приоритетные сценарии приёмки order lifecycle

1. PENDING + payment_status=pending + payment_method=card → PATCH CONFIRMED должен быть отклонён.
2. PREPARING + неполный checklist → любой API-путь в READY должен быть отклонён.
3. Категория с обязательным фото, но без approved ready_photo → READY должен быть отклонён через все API-пути.
4. DELIVERED → PATCH REFUNDED не должен менять статус без успешного refund workflow.
5. Два конкурентных перехода из одного статуса через разные API/подключения PG15 и PG18.
6. Клиент, назначенный кондитером на чужой заказ и имеющий роли CUSTOMER+CONFECTIONER, не может завершить заказ как покупатель.
7. Любой courier может менять только назначенные ему deliveries; прямые PATCH и handoff не должны обходить назначение/доказательство передачи.
8. Каждый успешный переход имеет одну запись истории, один доменный event ID и восстанавливаемые side effects.
