## B. Реализованная функциональность

### Поставщик (SUPPLIER)
- **Профиль компании**: создание через upsert `PUT /api/supplier/profile` (id генерируется сервером), 20 полей (компания, ИП/ООО, ИНН, контакты, регион, описание, 15 категорий, оптовые условия, мин. сумма/партия, график, география, доставка/самовывоз).
- **Статусы**: draft → submitted → under_review → approved / rejected / changes_requested → suspended; серверные переходы, поставщик не может сам себе назначить approved (только admin action, доказано тестом).
- **Правила редактирования**: draft/changes_requested/rejected/approved — можно; submitted/under_review — 409; suspended — 409 (сервер).
- **Отправка на модерацию**: `POST /api/supplier/profile/submit` с валидацией обязательных полей (email, категория, контакты…), CAS по статусу, уведомления админам (SUPPLIER_SUBMITTED, dedup) и ack поставщику.
- **Каталог и остатки** (`/api/supplier/warehouse`): CRUD товаров, статусная машина draft/published/archived, публикация только при verificationStatus=approved (403 иначе), пополнение остатка через действие `restock` с журналом IN (напрямую quantity менять нельзя — 400), видимость «остаток/резерв/доступно».
- **Закупочные заказы** (`/api/supplier/orders` + `[id]/action`): входящие только свои (изоляция), подтверждение (с корректировкой согласованных количеств), отклонение с обязательной причиной ≥10 симв., обработка → готовность к отгрузке (с датой) → отгрузка; CAS по статусу.

### Модерация (ADMIN)
- **Очередь** `GET /api/admin/suppliers?status=…`: серверная фильтрация + summary-счётчики; UI `AdminSupplierVerification` (вкладка «Поставщики» в админ-дашборде) — карточка с данными компании/владельцем/категориями/комментарием модератора.
- **6 действий** `POST /api/admin/suppliers/[id]/action`: start_review, approve, reject (причина обязательна), request_changes (замечания обязательны), suspend (approved→suspended, каталог скрыт), resume. Каждое: роль на сервере, допустимость перехода (CAS по verificationStatus), запись в `supplier_profile_reviews` (автор, роль, причина), уведомление поставщику (SUPPLIER_APPROVED / VERIFICATION_REJECTED / SUPPLIER_CHANGES_REQUESTED / SUPPLIER_SUSPENDED).

### Каталог / цены / остатки
- Цены — целые копейки (INTEGER), плавающая точка не используется; единицы измерения: kg/g/liter/ml/piece/box/pack (CHECK-констрейнт, наследован).
- MOQ (`min_order_qty`) и кратность (`order_step`): валидация `(qty - moq) % step === 0 && qty >= moq` — сервер (юнит + интеграционно).
- Остатки: физический `quantity`, `reserved_quantity`, доступное = разница; CHECK-констрейнты `reserved_quantity >= 0`, `reserved_quantity <= quantity`, `quantity >= 0`; журнал `supplier_product_movements` (RESERVE/RELEASE/OUT/IN/ADJUST) с привязкой к заказу.
- Резерв: жёсткий при создании заказа (SUBMITTED) — атомарная транзакция `SELECT … FOR UPDATE`; освобождение при reject/cancel; release+OUT при доставке. Подтверждение с корректировкой освобождает излишек резерва в той же транзакции.

### Поиск для кондитера
- `GET /api/suppliers` — публичный список одобренных+активных (без приватных контактов; email/телефон/ИНН не отдаются), счётчик опубликованных товаров, фильтры регион/категория/поиск.
- `GET /api/b2b/catalog` — переписан: только published-товары одобренных поставщиков (server-side видимость через ID-набор), фильтры q/категория/поставщик/единица/цена/наличие, сортировка; draft/архив/неодобренные невидимы (доказано негатив-тестами).
- UI `supplier-shop-page.tsx` переписан с MOCK на реальные данные: витрина поставщиков + каталог + закупочная корзина (один поставщик на заказ) + оформление (способ получения, дата, адрес, комментарий, Idempotency-Key).

### Закупочные заказы
- Статусная машина: DRAFT→SUBMITTED→CONFIRMED→PROCESSING→READY_FOR_SHIPMENT→SHIPPED→DELIVERED; REJECTED / CANCELLED / DISPUTED. Матрица `ACTION_TRANSITIONS` в `src/lib/purchase-orders.ts` (buyer/supplier/admin; админ не вмешивается).
- Создание `POST /api/purchase-orders`: роль CONFECTIONER, серверная цена из БД (клиентская не доверяется), MOQ/остаток/публикация/одобрение поставщика, идемпотентность через `Idempotency-Key` (partial unique index + возврат existing), номер PO-YYYY-NNNN через sequence.
- Обработка покупателем `PATCH /api/purchase-orders/[id]`: cancel (до PROCESSING), confirm_delivery (SHIPPED→DELIVERED + списание), dispute (активные), просмотр своей карточки/истории.
- История: `purchase_order_status_history` (from/to, автор, роль, комментарий) — видна обеим сторонам.

### Уведомления
- Существующий `sendNotification` (dedupKey от повторов). Новые шаблоны: SUPPLIER_SUBMITTED (админам), SUPPLIER_PROFILE_SUBMITTED, SUPPLIER_APPROVED, SUPPLIER_CHANGES_REQUESTED, SUPPLIER_SUSPENDED; события закупок используют существующие ORDER_* шаблоны с осмысленными title/body (`notificationForAction`). Дубли подавлены dedupKey (доказано идемпотентными повторами).

## C. Архитектура

**Переиспользовано:** `getUserFromRequest`/`requireRole` (RBAC через user_roles), csrfFetch-паттерн, supabaseAdmin + getPool(), паттерн CAS-обновлений (Z-v14), `sendNotification` с dedup, RLS-паттерн «SELECT участникам, мутации — service role», существующие таблицы supplier_profiles/supplier_products, статусные шаблоны ORDER_*.

**Новые миграции:** `supabase/migrations/0064_supplier_procurement.sql` — расширение supplier_profiles (+21 колонка модерации/профиля), supplier_products (+11 колонок: status, reserved_quantity, min_order_qty, order_step…), 3 новые таблицы (supplier_profile_reviews, supplier_product_movements, purchase_orders + purchase_order_items + purchase_order_status_history), sequence, RLS + политики, CHECK-констрейнты, идемпотентно.

**Новые API (10):** `/api/supplier/profile` (GET/PUT), `/api/supplier/profile/submit`, `/api/admin/suppliers` (GET), `/api/admin/suppliers/[id]/action`, `/api/suppliers` (GET публичный), `/api/purchase-orders` (GET/POST), `/api/purchase-orders/[id]` (GET/PATCH), `/api/supplier/orders` (GET), `/api/supplier/orders/[id]/action` (POST). **Переписаны:** `/api/b2b/catalog` (битый → рабочий), `/api/supplier/warehouse` (битые колонки quantity_available/price_per_unit → реальные; полный CRUD).

**Изоляция данных:** поставщик видит/меняет только свой профиль, свои товары, свои входящие заказы (supplier_id = user.id на сервере); кондитер — только свои закупки (buyer_id = user.id); чужой доступ → 403/404 (доказано). RLS включён на всех новых таблицах.

**Конкурентность:** резерв и смена статуса — в одной транзакции с `FOR UPDATE`; CAS `WHERE status = expected` → проигравший получает 409; идемпотентность создания через уникальный ключ; двойного резерва нет (доказано гонкой).

## E. Незакрытые проблемы

**Не реализовано (осознанно, вне v17):**
- Финансовые взаиморасчёты с поставщиками (оплата закупок) — платёжная архитектура не поддерживает B2B-расчёты безопасно; в UI явно указано «Оплата не списывается».
- Разрешение споров (DISPUTED → финальный статус) — только фиксация спора обеими сторонами; разрешение — следующий этап (admin tooling).
- Загрузка фотографий товаров поставщика через upload-инфраструктуру — колонка `image_url` есть, но UI-загрузчик не подключён (защищённые upload-файлы не трогались осознанно).
- Пагинация/бесконечный скролл каталога (limit 200, offset — есть, UI-пагинации нет).
- Email-дубли уведомлений о заказе админам при большом числе админов (in_app only — ограничено каналами шаблона).

**Частично:** витрина поставщиков показывает публичные данные, но отдельной карточки поставщика (модал) нет — вся витрина на фильтрах; `confirmed_subtotal` отображается обеим сторонам, но нет явного «принятия изменений кондитером» (считается согласованным по факту подтверждения).

**Не проверено:** CI GitHub Actions (сборка Docker) — push не выполнялся (нет credentials, отдельное разрешение требовалось и не запрашивалось для v17).

**Риски следующего этапа:** 1) при большом числе заказов вычисление резерва через movements-подзапрос потребует индекса-аккумулятора; 2) drop-поддержка WHOLESALER/wholesale_prices осталась нетронутой (не дублировала); 3) `inventory_items`-менеджер поставщика (внутренний склад) существует параллельно с каталогом продаж — UI разграничен, но объединение желательно.
