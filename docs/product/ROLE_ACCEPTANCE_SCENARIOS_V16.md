# ROLE ACCEPTANCE SCENARIOS — Z-v16

Проверяемые пользовательские сценарии по ролям с критериями успеха. Формат каждого сценария: **предусловие → шаги → критерий успеха (UI+API+DB)**. Сценарии маркированы: ✅ — уже проверен в Z-v16; 🔜 — готов к прогону (после соответствующих задач backlog); ⛔ — заблокирован продуктовым решением/пробелом.

Общие критерии для всех сценариев (если не указано иное):
- операция видна в UI и завершается явным статусом (toast/изменение состояния);
- данные сохранены в БД (проверка прямым SQL или API);
- после F5 и повторного входа результат сохраняется;
- при ошибке API: явное сообщение об ошибке, НЕТ ложного успеха, данные не меняются;
- повторный/двойной запрос не создаёт дублей;
- чужой пользователь / не-авторизованный получает 401/403, данные недоступны.

## 1. CUSTOMER (покупатель)

### C-1. Регистрация и вход ✅
Предусловие: чистый браузер.
1. Открыть `/` → «Войти» → вкладка «Регистрация» → роль «Покупать торты».
2. Заполнить имя/телефон/email/пароль, оба обязательных согласия.
3. «Зарегистрироваться».
Успех: аватар в шапке; в БД profiles + user_roles(CUSTOMER, is_active); повторный вход по email/паролю работает; отказ при существующем email — явная ошибка.

### C-2. Поиск и карточка товара ✅ (частично)
1. `/catalog` → фильтр по категории/цене → открыть товар.
Успех: карточка показывает фото/состав/цену из `/api/products/[id]`; данные совпадают с БД.
⚠️ Известное ограничение: фильтры клиентские по снимку ≤60 товаров (P2).

### C-3. Корзина и checkout готового товара ✅ (покрыт e2e U-07)
1. Добавить 2 товара → изменить количество → применить промокод → checkout.
Успех: итог = серверный пересчёт; в БД orders + order_items + payments; идемпотентный повтор (тот же Idempotency-Key) не создаёт второй заказ; корзина очищена после успеха; при недоступности окна — баннер + 422 без создания заказа.

### C-4. Оплата YooKassa 🔜 (нужны боевые ключи; в dev — mock-путь)
1. После checkout → оплатить → webhook payment.succeeded.
Успех: payments.payment_status=escrow; financial_ledger запись; повтор webhook идемпотентен; canceled → заказ CANCELLED без refund.

### C-5. Поддержка: эскалация оператору ✅ (Z-v16)
Предусловие: аккаунт покупателя.
1. Открыть чат-виджет → комната «Поддержка Уездного».
2. Отправить «Оператор, помогите разобраться!».
Успех: сообщение в chat_messages (channel_id); **в chat_escalations ровно одна запись** (reason=manual_request, priority=high, status=pending, metadata.message_preview=текст); повтор «Оператор…» НЕ создаёт вторую запись (дедуп по открытым статусам); сообщение оператора появляется в чате после F5; колокол: «Оператор поддержки написал вам» с переходом в чат.
Проверено: 2026-11-08, аккаунт z16-cust-e2e@test.local.

### C-6. Отмена заказа ✅
1. Дашборд → заказ PENDING → «Отменить».
Успех: статус CANCELLED, order_status_history с актёром; при оплаченном — refund-заявка/возврат; гонка двух отмен → 409 у проигравшего; кондитер видит статус у себя.

### C-7. Отзыв ✅
1. Заказ DELIVERED → «Оставить отзыв» → оценка+текст+фото.
Успех: product_reviews запись; повтор на тот же заказ → 409; отзыв появляется в карточке товара (approved-поток).

### C-8. Возврат (заявка) ✅ (частично, без e2e на полный цикл)
1. Заказ оплачен → «Вернуть средства» → форма.
Успех: refunds.status='requested'; админ видит заявку; исполнение только ADMIN/SUPER_ADMIN; финал статуса — только через webhook refund.succeeded.

## 2. HOME (кондитер)

### H-1. Онбординг и модерация ✅
1. Регистрация с ролью «Продавать торты» → заполнить профиль → отправить на верификацию (≥30 симв., ≥3 фото).
Успех: confectioners.pending; админ approve → verified=true; кондитер может публиковать (canPublishProducts); reject без reason ≥10 симв. — 422.

### H-2. Каталог: создать товар ✅
1. Кабинет → Каталог → «Добавить» → title/цена/описание/начинки → сохранить → опубликовать.
Успех: products.published; товар появляется в /catalog (LiveProductsHydrator); PATCH чужого товара — 403.
⚠️ Варианты/размеры (product_variants) — не подключены (P2).

### H-3. Заказ: accept с гейтом дефицита ✅
1. Покупатель создаёт заказ на товар из склада с остатком 1.
2. Кондитер: accept → успех, PREPARING, уведомление.
3. Второй параллельный accept → 409 ORDER_NOT_FEASIBLE/409 CAS.
Успех: accept-гейт читает inventory; история статусов одна запись у победителя; dedupKey уведомления.

### H-4. Склад: атомарное движение ✅
1. Приход 10 → списание 4 → остаток 6; журнал inventory_movements.
2. Параллельные 8 списаний по 1 при остатке 5 → 5 применено / 3 отклонено, отрицательного нет (U-11).

### H-5. Производственный цикл 🔜
1. PREPARING → чеклист → фото готовности → READY → передача.
Успех: ready-гейт требует чеклист+фото для тортовых категорий; handoff → IN_DELIVERY; capacity-резерв released.

### H-6. Выплата ✅ (API), 🔜 (UI)
1. Кабинет → Финансы → (сейчас кнопка disabled — P1).
2. API: POST /api/payouts/request с 2FA.
Успех: payout_requests; резерв заказов (payout_reserved_at CAS); отмена заказа с резервом — 409; admin approve→complete; формула = computeOrderPayout ( commission 15% снапшот + 2.5% эквайринг).

2. SUPPORT → кабинет → список эскалаций → видит pending с именем/превью/приоритетом.
