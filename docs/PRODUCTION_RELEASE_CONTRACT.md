# Контракт production-релиза Conditera

Дата фиксации: 18.11.2026

## 0. Физическое размещение production — локальная машина владельца

- Production размещается на локальной машине владельца проекта с белым (публично маршрутизируемым) IP-адресом. VPS, облачный сервер или перенос рабочей системы на внешний хостинг не являются целевой архитектурой.
- `conditera.ru` и необходимые поддомены должны разрешаться на публичный IP этой машины; если используется маршрутизатор, на нём настраивается перенаправление только TCP 80/443 на локальный reverse proxy.
- Caddy принимает внешний HTTP/HTTPS, получает и автоматически продлевает TLS-сертификаты, перенаправляет HTTP на HTTPS и маршрутизирует запросы к локальным сервисам.
- Из интернета доступны только необходимые публичные web/API endpoints. PostgreSQL, Supabase internal ports, Redis, n8n editor, админ-интерфейсы, Docker API и файловые хранилища не публикуются напрямую.
- Система должна автоматически запускаться после перезагрузки локальной машины и восстанавливаться после перезапуска контейнеров/процессов; проверяются DNS, NAT/firewall, TLS, внешний доступ не только из LAN, а также сценарий потери интернет-соединения и возврата питания.
- Резервные копии хранятся отдельно от рабочего диска/томов локальной машины; наличие только локальной копии не считается достаточной защитой.
- Деплой выполняется на локальный хост владельца. GitHub Actions может собирать и проверять артефакты, но не заменяет локальный production-хост и не разворачивает сервис в облаке.

Этот документ фиксирует обязательные условия релиза. Отчёт агента или факт запуска контейнера не заменяет проверку работающего пользовательского сценария.

## 1. Единый Supabase Runtime и PostgreSQL 17

- Для рабочей системы используется один согласованный кластер PostgreSQL 17.12 и один журнал прикладных миграций.
- Supabase runtime запускается одним Docker-контейнером: PostgreSQL, GoTrue, PostgREST, Realtime, Storage, Imgproxy, Postgres Meta, Kong и Edge Runtime управляются supervisor внутри образа. Next.js, Caddy и остальные прикладные сервисы остаются отдельными контейнерами.
- Канонический Compose-граф формируется тремя файлами через scripts/compose-single-runtime.mjs. В нём активны supabase-runtime и web; отдельные PG15/PG18 и legacy Supabase services отключены профилями и launcher их не допускает.
- Next.js подключается к тому же PostgreSQL 17 через роль conditera_app. Auth, REST, Realtime и Storage используют тот же кластер; отдельной app-БД или второго Supabase PostgreSQL нет.
- Исходные базы пустые. Пользовательские данные переносить не требуется: PG17 создаётся с чистого volume, затем применяются системные и прикладные миграции. Dump/restore, CDC, объединение записей и сохранение пустых PG15/PG18 volumes не являются частью перехода.
- Старые каталоги и volumes PG15/PG18 не подключаются к PG17. Их автоматическое удаление не выполняется. После первого production запуска обязательны регулярные резервные копии PG17 и проверка восстановления.
- Проверка CI на чистом PG17 подтверждает миграции, расширения, роли, RLS, конкурентные операции, полный lifecycle заказа, оплату, checkout, идемпотентность, отзывы, чат, рецептуры, склад, медиа, production build и Playwright.
- Отдельный runtime smoke подтверждает сборку/запуск единого Supabase контейнера, Auth signup, REST/OpenAPI, Realtime health и Storage upload/download.
- Эти проверки не равны production deployment. До публичного запуска обязательны нагрузочная проверка, проверка restart/recovery каждого supervised процесса, security review, DNS/TLS, реальные OAuth/YooKassa/Telegram credentials и контрольный заказ.
- Известные ограничения POC: часть Edge Functions возвращает not_implemented, Telegram notification channel требует настройки, Telegram/YooKassa webhooks должны идти через защищённые Next.js API routes. Нельзя объявлять все интеграции готовыми по факту успешного PG17 smoke.
- scripts/deploy.sh — канонический локальный production launcher: он проверяет env-файлы, собирает единый runtime, ждёт PG17 и Next.js health, проверяет миграционный ledger. .github/workflows/deploy.yml остаётся заблокированным, потому что он рассчитан на удалённый VPS, а целевой хост — локальный Windows-компьютер владельца. CI не разворачивает систему вместо него.

## 2. OAuth — обязательные провайдеры

Пользователь должен иметь отдельные способы входа:
- Яндекс;
- VK ID (современный VK ID, не устаревший oauth.vk.com flow);
- Google.

Общие требования:
- Authorization Code Flow; для VK ID — PKCE по актуальной спецификации VK ID.
- state проверяется на callback; для OIDC также проверяются nonce, issuer, audience, подпись и срок действия ID token.
- Redirect URI фиксированы и совпадают с настройками провайдера.
- Секреты находятся только в серверных runtime-переменных; никогда не попадают в клиентский bundle, Git, логи или Docker build args.
- Повторный запуск OAuth блокируется на время перехода к провайдеру.
- Отмена/ошибка возвращает пользователя на экран входа с понятным сообщением.
- returnTo проверяется как локальный относительный путь; открытые редиректы запрещены.
- Существующий пароль пользователя никогда не меняется при OAuth-входе.
- Связывание OAuth-идентичности с существующей учётной записью выполняется только безопасным подтверждённым сценарием; совпадение email само по себе не является достаточным доказательством владения.
- После первого входа создаются профиль и CUSTOMER-роль идемпотентно; сохраняется provider subject/id, чтобы идентифицировать пользователя независимо от изменения email.
- Callback, обмен токена, создание/связывание пользователя, cookies и выход должны быть покрыты автоматическими тестами.

## 3. Единый пользователь и единая модель сессии

- Supabase Auth/GoTrue — канонический источник сессии, если он выбран целевой моделью.
- Нельзя незаметно выдавать параллельно несовместимые JWT для разных частей приложения.
- Все API, SSR, браузерный клиент, Socket.IO и кабинеты используют согласованный механизм проверки токена и ролей.
- Роли загружаются из user_roles; клиентский выбор роли не является источником полномочий.
- Запрещено автоматически назначать повышенные роли через публичную регистрацию или OAuth.

## 4. Юридические и продуктовые требования

- Перед сбором персональных данных пользователь получает отдельные, конкретные согласия и ссылки на действующие документы.
- Фиксируются версии документов, дата/время и доказательство принятия условий.
- Персональные данные граждан РФ обрабатываются с соблюдением требований локализации и применимых требований 152-ФЗ.
- Для маркетплейса определяются фактические роли платформы, продавца/исполнителя и платёжного агента/оператора; юридическая модель подтверждается специалистом до публичного запуска.
- Заказ фиксирует состав изделия, параметры, аллергенную/пищевую информацию при наличии, цену, сроки, доставку, версии ТЗ и согласования сторон.
- Возвраты, претензии, чеки, рекламные материалы и отзывы имеют проверяемый жизненный цикл и журнал действий.

## 5. Release Gate

Релиз разрешён только после:
1. успешного production build;
2. typecheck, lint и полного набора тестов;
3. тестов регистрации, входа, восстановления доступа и каждого OAuth-провайдера;
4. проверки ролей и изоляции данных;
5. сценария заказа от формирования ТЗ до оплаты/отмены/возврата;
6. проверки Storage, чатов, уведомлений и фоновых задач;
7. резервного копирования и тестового восстановления БД и Storage;
8. проверки HTTPS, заголовков безопасности, rate limits, логирования и мониторинга;
9. проверки с чистого запуска и после рестарта сервера;
10. ручного подтверждения юридических документов ответственным специалистом.

## 6. Запреты при выпуске

- Не выполнять docker compose down -v, volume rm, db reset, очистку Storage или seed-команды на production.
- Не пушить изменения в main и не разворачивать их на production без отдельного согласования владельца.
- Не считать OAuth готовым по наличию кнопки или сформированного URL.
- Не считать Supabase готовым по одному успешному health-check PostgreSQL.
