# Контракт production-релиза Conditera

Дата фиксации: 18.11.2026

Этот документ фиксирует обязательные условия релиза. Отчёт агента или факт запуска контейнера не заменяет проверку работающего пользовательского сценария.

## 1. Supabase и Docker — обязательное ограничение владельца проекта

- Запрещено разворачивать Supabase как набор независимо управляемых Compose-проектов или разносить его компоненты по разным Docker-сетям.
- Запрещено создавать параллельные экземпляры PostgreSQL для одной рабочей системы.
- Для приложения должна существовать одна согласованная база PostgreSQL и один согласованный набор схем/миграций.
- Нельзя удалять, пересоздавать или очищать существующие volumes, базы, Storage и пользовательские файлы в рамках исправления инфраструктуры.
- Перед изменением инфраструктуры обязательны резервная копия и проверка восстановления.
- Обязательное требование владельца: весь Supabase runtime должен работать в ОДНОМ Docker-контейнере, а не в наборе контейнеров Compose. Внутри образа процессы PostgreSQL, GoTrue, PostgREST, Realtime, Storage и API gateway управляются supervisor; для каждого процесса предусмотрены readiness/health checks, перезапуск, корректное завершение и централизованные логи. Не включать Studio/Analytics/Vector в обязательный runtime без подтверждённой необходимости. Caddy, Next.js и прочие прикладные сервисы могут оставаться отдельными контейнерами, но Supabase-компоненты — нет.
- Официальная self-hosted Docker-дистрибуция Supabase запускает сервисы отдельными контейнерами вокруг одного PostgreSQL. Native runtime запускает сервисы процессами без Docker, но находится в Public Alpha и позиционируется для local development/CI; production-перевод на него без отдельного нагрузочного, restart/recovery и security-пилота запрещён.
- Нельзя использовать неподдерживаемую сборку как production без проверки запуска после рестарта, восстановления после отказа отдельного процесса, миграций, RLS, Auth, Storage и Realtime.
- В рабочей ветке `spike/supabase-single-container-runtime` и draft PR #21 подготовлена конфигурация с одним PostgreSQL `supabase/postgres:17.6.1.136`, одной БД `conditera` и общим endpoint для приложения/Supabase. Второй DB service удалён из overlay Compose; старые PG15/PG18 volumes не удалялись, не форматировались и не подключались к PG17.
- GitHub Actions run #295 успешно проверил 61 миграцию на Supabase PostgreSQL 17, тестовое объединение официального Supabase PG15 Auth/Storage с бизнес-схемой Conditera из PG18 в одну БД PG17, ссылки профилей на Auth-пользователей, Compose config, Next.js build, lint/typecheck и unit tests.
- Эта проверка использовала синтетические тестовые данные. Инвентаризация фактических строк в старой PG15 public-схеме и их сверка с PG18 business data **ещё не завершена**. До такой инвентаризации, конфликто-сверки, проверенного backup/restore и отдельного разрешения владельца нельзя выполнять production cutover.
- Supabase services (GoTrue, REST, Realtime, Storage, Kong, Studio и прочие) пока остаются отдельными контейнерами, хотя используют один PostgreSQL и одну БД. Обязательное требование владельца запустить полный Supabase Runtime в одном Docker-контейнере пока **не выполнено**. Edge Runtime также отсутствует в текущем Compose overlay.
- `scripts/deploy.sh` теперь требует уже работающий PG17, проверяет версию и создаёт backup БД/Storage до запуска migrator; он отказывается автоматически переключать PG15/PG18 или создавать пустую БД. Это не заменяет production migration/cutover plan. Workflow `.github/workflows/deploy.yml` и остальные release-paths отдельно требуют проверки перед использованием.
- Пока фактический production cutover, проверка OAuth callback на реальном self-hosted Auth, Storage файлов, Realtime и всех пользовательских сценариев не пройдены, релиз `conditera.ru` не считается готовым.

## 2. OAuth — обязательные провайдеры

Пользователь должен иметь отдельные способы входа:
- Яндекс;
- VK ID (современный VK ID, не устаревший oauth.vk.com flow);
- Google.

Общие требования:
- Authorization Code Flow; для VK ID — PKCE по актуальной спецификации VK ID.
- state проверяется на callback; для OIDC также проверяются nonce, issuer, audience, подпись и срок действия ID token.
- Redirect URI фиксированы и совпадают с настройками провайдера.
- Секреты находятся только в серверных runtime-переменных; никогда не попадают в клиентский bundle, Git, логи или Docker build args.
- Повторный запуск OAuth блокируется на время перехода к провайдеру.
- Отмена/ошибка возвращает пользователя на экран входа с понятным сообщением.
- returnTo проверяется как локальный относительный путь; открытые редиректы запрещены.
- Существующий пароль пользователя никогда не меняется при OAuth-входе.
- Связывание OAuth-идентичности с существующей учётной записью выполняется только безопасным подтверждённым сценарием; совпадение email само по себе не является достаточным доказательством владения.
- После первого входа создаются профиль и CUSTOMER-роль идемпотентно; сохраняется provider subject/id, чтобы идентифицировать пользователя независимо от изменения email.
- Callback, обмен токена, создание/связывание пользователя, cookies и выход должны быть покрыты автоматическими тестами.

## 3. Единый пользователь и единая модель сессии

- Supabase Auth/GoTrue — канонический источник сессии, если он выбран целевой моделью.
- Нельзя незаметно выдавать параллельно несовместимые JWT для разных частей приложения.
- Все API, SSR, браузерный клиент, Socket.IO и кабинеты используют согласованный механизм проверки токена и ролей.
- Роли загружаются из user_roles; клиентский выбор роли не является источником полномочий.
- Запрещено автоматически назначать повышенные роли через публичную регистрацию или OAuth.

## 4. Юридические и продуктовые требования

- Перед сбором персональных данных пользователь получает отдельные, конкретные согласия и ссылки на действующие документы.
- Фиксируются версии документов, дата/время и доказательство принятия условий.
- Персональные данные граждан РФ обрабатываются с соблюдением требований локализации и применимых требований 152-ФЗ.
- Для маркетплейса определяются фактические роли платформы, продавца/исполнителя и платёжного агента/оператора; юридическая модель подтверждается специалистом до публичного запуска.
- Заказ фиксирует состав изделия, параметры, аллергенную/пищевую информацию при наличии, цену, сроки, доставку, версии ТЗ и согласования сторон.
- Возвраты, претензии, чеки, рекламные материалы и отзывы имеют проверяемый жизненный цикл и журнал действий.

## 5. Release Gate

Релиз разрешён только после:
1. успешного production build;
2. typecheck, lint и полного набора тестов;
3. тестов регистрации, входа, восстановления доступа и каждого OAuth-провайдера;
4. проверки ролей и изоляции данных;
5. сценария заказа от формирования ТЗ до оплаты/отмены/возврата;
6. проверки Storage, чатов, уведомлений и фоновых задач;
7. резервного копирования и тестового восстановления БД и Storage;
8. проверки HTTPS, заголовков безопасности, rate limits, логирования и мониторинга;
9. проверки с чистого запуска и после рестарта сервера;
10. ручного подтверждения юридических документов ответственным специалистом.

## 6. Запреты при выпуске

- Не выполнять docker compose down -v, volume rm, db reset, очистку Storage или seed-команды на production.
- Не пушить изменения в main и не разворачивать их на production без отдельного согласования владельца.
- Не считать OAuth готовым по наличию кнопки или сформированного URL.
- Не считать Supabase готовым по одному успешному health-check PostgreSQL.
