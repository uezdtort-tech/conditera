## 2. Задача 2 — ревью `scripts/scan-evidence.mjs`: последнее правило понижения

### 2.1 Находка: H-1 (v4.3, `a9a0672`) был формально неверен

Правило `/^env presence-only: [^=\n]*$/` в `SYNTHETIC_CONTEXT` понижало ЛЮБОЙ
`real`-матч на строке-инвентаре без `=`. Его заявленный инвариант — «реальная
утечка — это `KEY=<value>` и никогда не совпадает с этим форматом строки» —
**опровержим**: JWT (base64url без паддинга), Bearer-токены, `Cookie: …`,
`postgres://user:pass@host`, значения в кавычках, `sk-…`-ключи совпадают со
своими `real`-правилами **без единого `=`**. Такое совпадение на
presence-only-строке молча понижалось бы до synthetic → пропуск настоящего
секрета. Это ослабление сканера без узкого формального основания.

### 2.2 Узкое формальное основание исправления (коммит `13a5947`)

Среди всех 10 `real`-правил только `supabase-service-role` может сработать на
name-only-строке без какого-либо значения: его альтернация
`SUPABASE_SERVICE_ROLE|…` — подстрока документированного ИМЕНИ переменной.
Каждое другое `real`-правило требует value-образного содержимого
(`-----BEGIN`, `Bearer <16+>`, `eyJ…`, `Cookie: <8+>`, токены
`sk-/ghp_/github_pat_/AKIA`, `://user:pass@`, `KEY=<value>`, пароль в кавычках) —
т.е. его срабатывание означает потенциальное значение. Следовательно:

- понижение ограничено парой (строка presence-only) × (категория
  `supabase-service-role`) — исходный кейс v4.3 остаётся зелёным;
- все value-образные правила остаются REAL на любой строке — ложный пропуск
  исключён по построению, а не по доверию к формату продюсера лога.

Сканер усилен, не ослаблен. Комментарий в коде переписан с формальным
обоснованием.

### 2.3 Доказательство тестами — 14/14 PASS (`scripts/verify/scan-evidence-rules-verify.mjs`)

Верификатор гоняет РЕАЛЬНЫЙ сканер-сабпроцесс на временных фикстурах (все
значения синтетические, каталог удаляется в finally):

- **A1–A6**: JWT / Bearer / Cookie / db-conn с кредами / пароль в кавычках /
  api-key на `=`-свободных presence-only-строках → сканер exit 1, FINDING по
  нужной категории (ложного пропуска НЕТ);
- **A7–A8** (регрессы `a9a0672`): `env presence-only: KEY=value` и обычный
  `KEY=value` → exit 1;
- **B1–B2**: мотивирующая строка v4.3 (инвентарь имён, включая
  `SUPABASE_SERVICE_ROLE_KEY SET`) и generic name-only → exit 0, synthetic
  (легитимный кейс не сломан);
- **C1–C3**: прецеденты E-1 (`[supabase/admin] … not set.`) и F-1

  значением не порождает db-conn-находки вовсе;
- **C4**: смешанный файл (легитимный инвентарь + реальный JWT) → exit 1 —

Полный дефолтный прогон сканера после сужения: **exit 0, real 0 / synthetic 317**
