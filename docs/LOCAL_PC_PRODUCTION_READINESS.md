# Подготовка Conditera к production на локальном ПК

Статус документа: план и контрольные условия. Это НЕ подтверждение готовности и НЕ разрешение на запуск, миграцию или переключение данных.

**Обновление 2026-11-24:** одно-контейнерный Supabase POC успешно собран и проверен в GitHub Actions (run [45494633668](https://github.com/uezdtort-tech/conditera/actions/runs/45494633668), commit `b94dd434`). Проверены Compose overlay, запуск ровно одного Supabase runtime-контейнера, процессы Supervisor, Auth signup, Storage upload/download и PostgreSQL schemas; временное окружение очищено. Это PASS только для изолированного POC, не для production cutover.

## Зафиксированная целевая среда

- Production-хост — локальный ПК владельца под Windows.
- Все компоненты запускаются в Docker Desktop (Linux containers / WSL2).
- Внешний трафик принимается через reverse proxy с HTTPS; наружу не публикуются PostgreSQL, Docker API, Redis, внутренние Supabase API и панели администрирования.
- Для всей рабочей системы используется один PostgreSQL-кластер и одна каноническая рабочая база.
- По требованию владельца весь обязательный Supabase runtime должен работать внутри ОДНОГО Docker-контейнера. Отдельные Supabase Auth/REST/Realtime/Storage/Kong контейнеры не считаются выполнением этого требования.
- Внутренние прикладные сервисы могут оставаться отдельными контейнерами, но используют единый Compose-проект, согласованную сеть и DNS-имена сервисов. Нельзя закреплять динамические IP контейнеров в конфигурации.
- Данные, Storage и резервные копии не должны зависеть от жизненного цикла контейнера; volumes не удаляются при обновлении приложения.

## Фактические блокеры, обнаруженные в репозитории

1. `docker-compose.yml` содержит `conditera-db` на `postgres:18-alpine`, базу `conditera`; приложение и migrator используют этот сервер.
2. `docker-compose.supabase.yml` содержит отдельный `conditera-supabase-db` на `supabase/postgres:15.6.1.141`, базу `supabase`; GoTrue, PostgREST, Realtime, Storage и другие Supabase-сервисы используют его.
3. Базовый `docker-compose.supabase.yml` по-прежнему содержит legacy отдельные Supabase-сервисы. Новый `docker-compose.supabase-single-container.yml` переводит их в legacy-профиль и подключает один `supabase-runtime`; его изолированный POC прошёл CI, но production Compose/cutover ещё не выполнены.
4. Исторический `scripts/deploy.sh` поднимал оба Compose-стека, применял только ограниченный список миграций и мог продолжать работу при ошибках отдельных миграций. Этот скрипт заблокирован отдельным safety-изменением до прохождения release gate.
5. `.github/workflows/deploy.yml` ориентирован на удалённый VPS через SSH и каталог `/opt/conditera`, а не на локальный Windows ПК владельца. Не запускать этот workflow для production Conditera.
6. Текущие файлы Compose не доказывают согласованность реальных контейнеров, сетей, DNS, портов, volumes и переменных на локальном ПК. Для этого требуется read-only проверка на самой машине.
7. Две существующие БД и их volumes считаются потенциально содержащими уникальные данные. До сверки запрещены удаление, очистка, пересоздание и прямое копирование PGDATA между major-версиями PostgreSQL.

## Что необходимо реализовать и проверить

### A. Единый Supabase runtime

- POC-образ Supabase all-in-one с контролируемым Supervisor уже реализован и прошёл изолированный CI smoke-test (см. статус выше).
- В POC проверены PostgreSQL, GoTrue, PostgREST, Realtime, Storage и API gateway; подтверждены Auth signup и Storage upload/download.
- Следующий этап — проверить этот runtime вместе с реальным web/chat/n8n/Caddy Compose-стеком и подготовить read-only сверку существующих БД/volumes на Windows ПК владельца.
- Для каждого процесса определить readiness, health check, политику перезапуска, корректное завершение, лимиты и централизованные логи.
- Проверить порядок запуска и зависимостей, обработку падения одного процесса, повторное подключение клиентов и восстановление после перезапуска контейнера.
- Зафиксировать совместимые версии компонентов и расширений. Не использовать плавающие теги образов.
- Локальные Next.js compatibility shims `/auth/v1`, `/rest/v1`, `/storage/v1` закрыты на production-origin; в production Supabase API должен идти только через `/api/*` → Caddy → Kong → единый Supabase runtime. Shims включаются в development и в явных CI-интеграционных тестах.
- POC не считается production-ready: ещё требуются интеграционные проверки приложения, нагрузочные и security испытания, backup/restore с реальным восстановлением, restart/recovery и проверка после перезагрузки Windows.

### B. Одна база и безопасный перенос

- Выполнить read-only инвентаризацию обеих существующих БД на локальном ПК.
- Сверить версии PostgreSQL, схемы, расширения, миграционные журналы, таблицы, индексы, ограничения, триггеры, функции, grants, RLS, sequences и фактические количества строк.
- Отдельно сверить `auth.users`, `profiles`, `user_roles`, OAuth identity links, заказы, платежи, возвраты, выплаты, складские движения, чаты и Storage.
- Сделать резервные копии обеих БД и Storage. Обязательно восстановить их в изолированную среду и проверить результат.
- Подготовить карту миграции, обработку конфликтов, cutover и обратный план.
- Не выбирать целевой кластер автоматически и не объединять пользователей только по совпадению email.
- Старые volumes сохранить неизменными до завершения периода наблюдения и отдельного разрешения владельца на удаление.

### C. Docker Desktop и сеть на локальном ПК

- Один Compose project и одна управляемая сеть для прикладных контейнеров.
- DNS-имена сервисов Compose вместо статических IP.
- Единый источник конфигурации для внутренних URL, портов, JWT, anon/service-role keys и секретов.
- Проверить отсутствие конфликтов портов и разночтений между адресами Windows-хоста и контейнеров.
- Проверить запуск после перезагрузки Windows, рестарт Docker Desktop, рестарт каждого контейнера, временную потерю интернета и восстановление.
- Проверить автозапуск, Windows Firewall, публичный DNS, маршрутизатор/NAT, доступность только необходимых портов и TLS.
- Внешние резервные копии должны храниться отдельно от рабочего диска локального ПК.

### D. Приложение и релиз

- Сохранить существующую концепцию Conditera, интерфейс, навигацию и согласованные пользовательские сценарии. Не переносить интерфейс Qwen и не менять продуктовую модель без отдельного согласования.
- Проверить регистрацию, вход, выход, обновление сессии, восстановление доступа и реальные OAuth-потоки Яндекс, VK ID и Google.
- Проверить роли и изоляцию данных на сервере, RLS и доступ к Storage.
- Проверить полный жизненный цикл заказа, согласование ТЗ, чаты, производство, склад, платежи, отмены и возвраты.
- На Windows перед production build выполнять `npm run env:check:prod`; для разработки — `npm run env:check`. Проверка реализована на Node.js и не требует Bash/Git Bash.
- Выполнить typecheck, lint, unit/integration tests, production build и полный Playwright E2E на целевом локальном runtime.
- Проверить health/readiness каждого процесса, резервное копирование и восстановление.
- Проверить юридические тексты, согласия, версии документов и применимые требования законодательства РФ; юридические формулировки должны быть подтверждены ответственным специалистом.

## Запреты до прохождения release gate

- Не запускать старый удалённый VPS workflow для production.
- Не запускать миграции на production и не переключать URL подключения.
- Не выполнять `docker compose down -v`, `docker volume rm`, `db reset`, очистку Storage или удаление PGDATA.
- Не менять major-версию PostgreSQL поверх существующего volume.
- Не публиковать изменения в `main), не объединять PR и не выполнять production deploy без отдельного подтверждения владельца.
- Не объявлять готовность по CI, одному health endpoint или успешному запуску только web-контейнера.

## Критерий готовности

Релиз считается подготовленным только после документированного успешного прогона на локальном Windows ПК: чистый запуск → Auth/OAuth → заказ → запись в единую БД → REST/RLS → Realtime → Storage → платежные и складские сценарии → backup → restore → перезагрузка ПК → повторная проверка. До этого момента статус — NOT READY.
