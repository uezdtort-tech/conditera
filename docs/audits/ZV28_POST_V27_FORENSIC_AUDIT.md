### 9.2. Ответы на 10 вопросов §6.2 (кратко)

1. Понятие версии рецепта есть ТОЛЬКО для marketplace-публикаций (recipe_versions)
   и производственных карт (card_versions); для товарных рецептов — нет.
2. Товарный рецепт правится на месте (recipes.recipe_ingredients — мутабельные).
3. История изменений товарного рецепта не ведётся.
4-5. Заказ рассчитывается по версии рецепта НА МОМЕНТ расчёта (accept/breakdown
   читают текущую); фиксация состава заказа = момент расчёта, не checkout.
6. Accept использует АКТУАЛЬНЫЙ рецепт (доказательство Z-v27: правка 250→500 г
   меняла required старого заказа и давала 409).
7. Да — изменение рецепта задним числом меняет потребность/дефицит/закупку истории.
8. Повторного списания нет (идемпотентность 0049/0071); повторный accept при
   изменившемся рецепте → 409 (безопасно, но блокирует процесс).
9. Связь: recipe (текущий) → products.recipe_id → order_items.product_id;
   journal: inventory_write_offs по (owner, order, signature) — от рецепта не зависит.
10. Цена/итоги заказа снапшотятся в order_items (безопасно); себестоимость
    ингредиентов считается от текущих складских цен (аналитический риск, не деньги
    клиента); производственные нормативы — у партий версионированы, у заказов — нет.

| Стоимость сопровождения | низкая | средняя-высокая | высокая |

**Рекомендация**: стартовать с **Варианта A** (Z-v27 предложение подтверждается
архитектурно: колонка metadata существует, обратная совместимость сохраняется,
fail-closed правило «нет снапшота — расчёт по текущему + явный признак в ответе»),
с последующей миграцией к **B/C** при появлении требований аудита рецептур.
`orders.metadata` — не «автоматически лучшее», а минимально достаточное при
текущей схеме: снапшот потребности (name, qty, unit, inventory_item_id?,NormHash)
+ schema_version внутри jsonb для эволюции формата.

### 9.4. Обязательные требования будущей реализации (§6.4) — покрыты Вариантом A
при соблюдении: снапшот пишется ТОЛЬКО сервером на checkout (не доверять клиенту);
нет снапшота → не «молчаливая подмена», а расчёт по текущему + флаг
`source: "live"|"snapshot"` в breakdown/acceptance; повторный accept не списывает
повторно (уже обеспечено 0049/0071); старые заказы не ломаются.

### 9.5. План внедрения (для отдельного этапа, НЕ выполняется)

1. Схема: без DDL (metadata существует) ИЛИ опционально generated-колонка/индекс
   по metadata->'acceptance_snapshot'; решение — на этапе реализации.
2. Типы: `AcceptanceSnapshotIngredient {name, qty, unit, inventoryItemId|null}`,
   `AcceptanceSnapshot {schemaVersion, createdAt, items[]}`.
3. Checkout (`src/app/api/checkout/route.ts`): после успешного гейта собрать
   потребность (`computeIngredientNeeds`/breakdown-путь) и записать в metadata.
4. Accept/`checkOrderAcceptance`: если metadata.acceptance_snapshot есть —
   рассчитывать shortages от снапшота (флаг source=snapshot), иначе live.
5. Breakdown/purchase-draft: аналогично (с пометкой источника).
6. Backfill: НЕ выполнять для старых заказов (остаются live-семантикой) —
   либо отдельное решение владельца.
7. Legacy-поведение: без снапшота = сегодняшнее (задокументировать).
8. Тесты: checkout пишет снапшот; правка рецепта НЕ меняет accept/breakdown
   старого заказа; новый заказ по новой рецептуре; конкурентные заказы на разных
   версиях; отсутствие снапшота → live + явный флаг.
9. Идемпотентность: повторный checkout той же корзины — снапшот перезаписывается
   только до оплаты; после оплаты metadata.acceptance_snapshot иммутабелен.
10. Rollback: фича-флаг (env) на чтение снапшота; откат = все считают live.
11. Контроль целостности: сверка count(orders WHERE paid AND metadata IS NULL)
    до/после релиза; ручной smoke на паре заказов.
