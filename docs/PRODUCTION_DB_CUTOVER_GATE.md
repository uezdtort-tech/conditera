# Блокировка production до объединения PostgreSQL

Дата аудита: 2026-11-21.

## Фактическая топология

В текущем Compose работают два независимых кластера:

- **Основной PostgreSQL 18** — подключение приложения через `DATABASE_URL` и `src/lib/postgrest/pool.ts`. Производственные операции, склад, рецептуры, capacity reservations, domain events и операционные API используют этот путь.
- **Supabase PostgreSQL 15** — подключение через `SUPABASE_INTERNAL_URL` → Kong/PostgREST/GoTrue/Storage. Auth, Supabase Admin, каталог, quote requests, платежи и часть order API используют этот путь.

Это отдельные кластеры и отдельные транзакционные области. Наличие одинаковых таблиц и UUID в обоих кластерах не означает, что строки синхронизированы.

## Последствие для индивидуального заказа

Путь индивидуального заказа пересекает оба кластера:

1. Покупатель создаёт `quote_requests` через Supabase Admin (PG15).
2. Кондитер выбирает производственный товар и рецепт, которые проверяются через основной PG18.
3. Фото и метаданные RFQ хранятся в Supabase Storage и таблице метаданных Supabase (PG15).
4. Обычный checkout и payment ledger используют Supabase Admin (PG15).
5. Производственный контур читает и изменяет заказы, рецептуры и склад через прямой PG Pool (PG18).

Без подтверждённой синхронизации нельзя считать, что оплаченный заказ из PG15 гарантированно существует в PG18 и доступен кондитеру. Обычный E2E на одной локальной БД этого не доказывает.

## Защитное поведение кода

- API принятия индивидуального предложения выполняет проверку рецепта, склада, срока и производственной мощности.
- В production этот API возвращает `503 DATABASE_TOPOLOGY_NOT_READY`, если явно не установлено `CONDITERA_UNIFIED_DATABASE=true`.
- Локальный E2E с loopback-only payment stub может проверять функциональность на одной тестовой БД.
- Не устанавливать `CONDITERA_UNIFIED_DATABASE=true` в production до выполнения всех пунктов cutover gate ниже.
- Миграции 0083–0085 описывают атомарный путь для единой БД. Их успешное применение в PG17/CI не является доказательством, что обе реальные production-БД уже объединены.

## Условия снятия блокировки

1. Снять отдельные проверенные резервные копии PG18 и PG15; восстановить обе копии в изолированных кластерах.
2. Зафиксировать канонический кластер, совместимый с Supabase, и версию PostgreSQL. Не менять major version поверх существующего PGDATA.
3. Сверить и объединить без потерь: `auth.users`, profiles, roles, confectioners, products, recipes, recipe_ingredients, inventory_items, quote_requests, confectioner_quotes, orders, order_items, payments, refunds, deliveries, production tables, domain_events и Storage metadata/files.
4. Для конфликтующих UUID и дублирующихся строк составить детерминированную карту переноса; не объединять пользователей только по email.
5. Перенести Storage-файлы и проверить их хеши, MIME, размер и доступ через Auth/RLS.
6. Переключить `DATABASE_URL`, `SUPABASE_INTERNAL_URL`, GoTrue, PostgREST, Realtime и Storage на один и тот же кластер только в тестовой репетиции.
7. Проверить создание пользователя, вход/refresh/revoke, RFQ, загрузку/просмотр вложений, ответ кондитера, выбор рецепта, принятие предложения, платёж/webhook, складское списание, фото готового изделия, выдачу/доставку и подтверждение покупателем.
8. Проверить отказ/повтор после сбоя на каждом шаге, восстановление из backup и план отката.
9. Только после письменного подтверждения владельца переключать production.

## Запреты

- Не запускать production deploy и не устанавливать флаг `CONDITERA_UNIFIED_DATABASE` до завершения cutover gate.
- Не удалять старые volumes, не выполнять `docker compose down -v`, не копировать PGDATA между major versions.
- Не считать успешный CI/PGlite/PG17/локальный E2E доказательством синхронизации production PG15 и PG18.
- Не сливать PR #49 и не публиковать main без отдельного разрешения владельца.
