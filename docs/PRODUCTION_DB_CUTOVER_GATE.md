# Production gate: единый PostgreSQL 17 и Supabase runtime

Дата актуализации: 2026-11-22.

## Зафиксированные решения владельца

- Все прежние базы пустые; пользовательских данных и рабочих заказов в них нет.
- Перенос, слияние, CDC, сверка UUID, синхронизация старых кластеров и окно переключения данных НЕ требуются.
- Целевая база Conditera — чистый PostgreSQL 17.12 в новом Docker volume.
- PostgreSQL 15/18 не являются целевыми production-версиями.
- Весь обязательный Supabase runtime (PostgreSQL, GoTrue, PostgREST, Realtime, Storage, Postgres Meta, Imgproxy, Kong, Edge Runtime) запускается внутри одного контейнера.
- Приложение, Auth, REST, Realtime и Storage должны работать с одной канонической БД.
- Production seeds выключены: `SEED_MODE=none`. Демоданные разрешены только в изолированных CI/E2E окружениях.

## Целевая топология

- `supabase-runtime`: единый контейнер Supabase на PostgreSQL 17.12.
- `web`: Next.js приложение; подключение к единой базе через роль `conditera_app`.
- `BACKUP_DATABASE_URL`: отдельная read-only роль `conditera_backup` с `pg_read_all_data` и `BYPASSRLS`, только для полного резервного копирования.
- `Caddy`: единственная публичная точка входа HTTPS.
- n8n и внутренние сервисы не публикуются наружу; интерфейс n8n доступен только локально.
- n8n 2.48.7 импортирует и публикует только проверенные workflow 01–05; непроверенные workflow-прототипы остаются неактивными и не импортируются.
- n8n получает только `CRON_SECRET` из секретов приложения; доступ к env в выражениях включён только для этих доверенных workflow, ключ шифрования передаётся отдельным Docker secret-файлом, а DB-пароли и `N8N_WEBHOOK_SECRET` в контейнер n8n не передаются.
- Источник workflow — Git; startup bootstrap синхронизирует опубликованное состояние и снимает публикацию у workflow, отключённых в репозитории.
- PostgreSQL, Redis, Storage API, Kong admin и Docker API не публикуются напрямую в интернет.
- Данные PostgreSQL, Storage, пользовательские медиа и резервные копии находятся в постоянных volumes/внешнем хранилище, а не в слое контейнера.

## Проверки в CI

Следующие проверки обязательны и должны быть зелёными на одном и том же актуальном SHA:

1. Чистый PG17.12: системные и прикладные миграции применяются с нуля.
2. Migration ledger точно совпадает с SQL-файлами репозитория; повторный `bun run db:setup` не меняет ledger и не ломает схему.
3. Auth, Storage, Realtime и PostgREST инициализируются на этом же PG17.
4. Создаются `conditera_app` и отдельная read-only роль `conditera_backup`; последняя реально выполняет `pg_dump` всех нужных схем, включая auth, storage и public.
5. Production Docker image приложения запускается с PG17.
6. На PG17 выполняются конкурентные возвраты, полный жизненный цикл заказа, checkout/idempotency, отзывы, чат, рецепты, склад, операционный центр, медиа и модерация.
7. Проверяются архив БД, проверка gzip, восстановление в чистую shadow-БД и сопоставление критичных таблиц.
8. Playwright проверяет публичные страницы, авторизацию, SEO, CSP, мобильную ширину и отсутствие необработанных JS-ошибок.
9. Supabase runtime POC проверяет Auth, Storage upload/download, Realtime, gateway, Edge Function ACL и полный backup через `conditera_backup`.

Успешный старый прогон на PG15, PGlite или отдельная проверка Compose не заменяет полный сценарный прогон на PG17. Проверка считается актуальной только для SHA, который является текущей вершиной PR/релизной ветки.

## Локальный production gate на Windows ПК владельца

CI не имеет доступа к Docker Desktop, дискам, Windows Firewall, роутеру, DNS и реальным секретам владельца. Поэтому перед первым production запуском на целевом ПК требуется:

1. Проверить Docker Desktop в Linux containers/WSL2, доступность диска и свободное место.
2. Сгенерировать секреты локально через `bash scripts/prepare-production-env.sh`; не коммитить и не отправлять их в чат/логи.
3. Заполнить реальные provider credentials отдельно: YooKassa, SMTP, Telegram, Yandex ID, VK ID и другие фактически включаемые интеграции.
4. Проверить redirect URI, webhook URLs, sender identity и тестовые транзакции провайдеров до включения боевых платежей.
5. Проверить DNS домена, NAT/port forwarding, Windows Firewall, TLS/HTTPS и доступность только 80/443 снаружи.
6. Запустить `bash scripts/deploy-single-container.sh --config` и устранить все ошибки preflight.
7. Выполнить первый запуск на новом пустом PG17 volume с `SEED_MODE=none`; не подключать старый PGDATA от PG15/18.
8. Проверить регистрацию, вход, refresh/revoke сессий, OAuth, создание индивидуального запроса, переписку, предложение кондитера, принятие предложения, оплату/webhook, складское списание, производство, фото готового изделия, передачу/доставку, возврат и спор.
9. Проверить backup и реальное восстановление БД и Storage в отдельные чистые volumes.
10. Проверить перезапуск контейнера и Windows/Docker Desktop, восстановление после потери сети и повторную проверку health.
11. До приёма реальных пользовательских данных включить автоматические ежедневные резервные копии, мониторинг свободного места, health checks и внешний off-host backup.

## Условия запрета релиза

Production не готов, если хотя бы одно из условий ниже не подтверждено фактически:

- полный актуальный CI на PG17 не зелёный;
- migration ledger не совпадает с репозиторием или повторное применение миграций ломает схему;
- хотя бы один из обязательных Supabase процессов не работает на единой PG17;
- роль резервного копирования не может создать и восстановить полноценный архив;
- E2E бизнес-сценарии, мобильные проверки, SEO, CSP или security checks провалены;
- реальные OAuth/платёжные/почтовые/webhook интеграции не настроены и не проверены в соответствующем тестовом контуре;
- локальный Windows production host, DNS, HTTPS, firewall и внешний backup не проверены;
- deploy preflight выдаёт ошибку.

## Явные запреты

- Не проектировать миграцию/слияние пользовательских данных из старых баз: они пустые.
- Не использовать PostgreSQL 15/18 как целевую базу.
- Не переносить PGDATA между major versions.
- Не удалять старые тестовые volumes автоматически; их наличие не является основанием для усложнения архитектуры.
- Не выполнять `docker compose down -v`, `docker volume rm`, `db reset` или очистку Storage в deploy-скрипте.
- Не запускать исторический удалённый VPS workflow: целевая среда — локальный Windows ПК владельца.
- Не включать production seeds.
- Не считать CI равным production deployment: реальный локальный хост, домен, DNS, HTTPS, секреты и провайдеры проверяются отдельно.

## Статус

**NOT READY до прохождения всех CI-проверок на актуальном SHA и локального production gate на Windows ПК.** Наличие подготовленного Compose/runtime и успешных отдельных тестов само по себе не означает завершённый production deployment.
