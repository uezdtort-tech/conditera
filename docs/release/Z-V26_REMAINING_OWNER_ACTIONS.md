# Z-v26 — REMAINING OWNER ACTIONS

Только конкретные действия владельца. Публикация (push/merge/deploy) остаётся запрещена до отдельного решения владельца.

## 1. Данные товара №1 «Свадебный торт «Ягодный бархат»» (разблокирует первый товарный заказ)

- **Что требуется**: ОДНО из двух значений по ингредиенту «Ягоды»:
  - (а) фактический остаток на складе кондитера «Сахарная печать» — создать/пополнить позицию `inventory_items` с ТОЧНЫМ именем «Ягоды» (единица «г», количество ≥ 250 г на торт), owner = `11111111-…-0101`; или
  - (б) реальная дата поставки для существующего черновика закупки `eaf5ae25-2fb9-4496-80ec-6e2573d9fcd7` — заполнить `expected_eta` (должна наступать раньше безопасного старта производства заказа).
- **Зачем**: снимает `LOW_STOCK` + `PURCHASE_ETA_MISSING` — единственные блокеры товара.
- **Где настраивать**: UI «Склад» (или SQL `inventory_items`), UI «Закупки» (поле ETA черновика).
- **Данные**: количество/единица (г) или календарная дата+время поставки. Источник — только ваша фактическая информация (система не придумывает остатки и ETA).
- **Кто предоставляет**: владелец (кондитер «Сахарная печать»).
- **Как проверить**: `node scripts/verify/p11-hardening-verify.mjs` (блок F1 уйдёт) → затем HTTP checkout товарной позиции → 200/201. Товар станет первым READY в карте Z-V26_CATALOG_DATA_READINESS.md.
- **Что заблокировано до выполнения**: любой товарный checkout (422). Custom-позиции конструктора работают уже сейчас.

## 2. Рецепты и привязки для остальных 11 товаров

- **Что требуется**: для каждого товара, который должен продаваться: рецепт (ингредиенты: имя, норма на 1 единицу, единица г/мл/шт/дес), привязка `recipe_id` на карточке товара, желательно `production_time_hours`. Справочно: 4 рецепта уже существуют в БД (см. карту готовности §«Существующие рецепты») — их можно привязать ТОЛЬКО если они соответствуют фактической рецептуре товара; в противном случае нужны ваши рецептуры.
- **Зачем**: без привязки гейт блокирует (`RECIPE_MISSING`) — осознанный контракт (запрет приёмки без расчёта ингредиентов).
- **Где**: UI «Рецепты» + карточка товара.
- **Кто**: владелец/технолог.
- **Проверка**: p11-hardening + checkout каждого настроенного товара.
- **Заблокировано до выполнения**: заказ этих 11 позиций. Альтернатива до настройки — временно скрыть неготовые товары из витрины (статус/draft) — решение владельца.

## 3. Склады кондитеров «Сладкая уездная» (-0102) и «Кондитерская Купеческая» (-0103)

- **Что требуется**: заведение позиций склада для этих двух кондитеров (сейчас 0 строк) — у их товаров (№6,7,8,10,11,12) нечего списывать даже при наличии рецептов.
- **Где**: UI «Склад» под соответствующими аккаунтами.
- **Проверка**: разбор заказа (/api/orders/[id]/breakdown) не должен показывать no_stock по позициям рецепта.

## 4. YooKassa sandbox

- **Что требуется**: `YOOKASSA_SHOP_ID` + `YOOKASSA_SECRET_KEY` (sandbox-пара), добавить в окружение (без вставки секретов в чат — файл `.env.local` на машине).
- **Зачем**: реальная оплата (сейчас честный stub `isStub=true`; в прод-режиме без ключей checkout 503 fail-closed).
- **Проверка**: sandbox-платёж на тестовом заказе → webhook `payment.succeeded` → статус заказа/payment. Реальные платежи не выполнять до решения о запуске.

## 5. OAuth Yandex ID

- **Что требуется**: зарегистрировать приложение в Яндекс ID, получить `YANDEX_CLIENT_ID`/`YANDEX_CLIENT_SECRET`, указать callback; внести в окружение.
- **Зачем**: вход через Яндекс (сейчас честный 501 fail-closed; email/password работает).
- **Проверка**: кнопка «Я Яндекс» → redirect → callback → сессия. VK ID — отдельно (не реализован; скрыть кнопку или завести задачу).

## 6. n8n workflow engine (опционально для запуска, не блокер витрины)

- **Что требуется**: развернуть n8n (Docker) и импортировать минимальные workflow: `order.created → уведомление`, `order.paid → задача кондитеру`. Сейчас работает только webhook-receiver (5678), события копятся, но не исполняются.
- **Проверка**: дашборд автоматизации показывает реальный статус из /api/health; тестовое событие проходит в execution history.

## 7. Email/SMTP и Telegram (не блокер)

- **Что требуется**: `SMTP_HOST/PORT/USER/PASS` и (опционально) `TELEGRAM_BOT_TOKEN` в окружение.
- **Зачем**: письма подтверждения и уведомления (сейчас fail-closed — заказы работают без них).
- **Проверка**: регистрация нового пользователя получает письмо; уведомление о заказе доставляется.

## 8. Решения по модельным наблюдениям (INFO, не блокеры)

1. **Версионирование рецептов**: правка рецепта меняет разбор исторических заказов (доказано изолированно, сценарий I). Если для бухгалтерии/претензий нужна неизменяемость — завести задачу на snapshot состава в заказ. Решение владельца.
2. **/register**: прямой URL не существует (404), регистрация доступна через модалку (/login и шапка). Если нужен прямой URL — отдельная малая задача.
3. **cart-sync**: рекомендация харденинга — добавить catch в `reconcile()` (сейчас сетевой сбой даёт console-error; ретраи корректны). Не блокер.
