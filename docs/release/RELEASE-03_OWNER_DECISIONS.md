## Q-3.1 — Частичный и полный возврат (рецепты)

**① Состояние кода.** Webhook `refund.succeeded` вызывает RPC `apply_yookassa_refund` (0039, кopecks-семантика, идемпотентность по provider refund id), затем — только при `fully_refunded === true` и `order.type === 'recipe'` — `revokeEntitlement(recipeId, buyerId)` (src/app/api/payment/webhook/route.ts:726-742; src/lib/recipes/entitlement.ts:83-95). Purchase route при повторном POST читает `refund_amount < amount` как признак «доступ ещё жив» (purchase/route.ts:111-114).

**② Фактическое поведение.** Полный возврат отзывает доступ. Частичный возврат доступ СОХРАНЯЕТ (и покупка, и Resolver считают частичный возврат совместимым с доступом: `refund_amount < amount`).

**③ Риск.** Покупатель, вернувший часть суммы, сохраняет полный доступ; при ручных частичных возвратах (не через webhook) entitlement не отзывается вовсе.

**④ Варианты.**
- **A (текущая реализация):** частичный возврат не отзывает доступ; полный — отзывает.
- **B:** любой возврат отзывает доступ (жёстче к покупателю, но частичный возврат часто компенсационный — отзыв будет восприниматься как штраф).
- **C:** пропорциональный пересчёт доступа (требует нового поля «доля доступа» и UI-семантики частичного контента — самая дорогая реализация).

**⑤ Рекомендация:** вариант A (как реализовано) — минимум сюрпризов, финансовая история сохраняется в orders/payments/refunds/ledger, повторная покупка реактивирует entitlement (РЕШ-6.2).

**⑥ Затронутое при смене решения:** webhook refund-ветка, entitlement.ts, purchase route, Resolver (правило 7), tests/e2e/recipe-purchase-flow.

**⑦ Тесты:** route.http.test.ts (8), route.test.ts (15), E2E payment-webhook-idempotency 24/24 (воспроизведено независимо 2026-11-09).

**⑧ Как есть:** поведение остаётся «полный возврат = отзыв», частичный = доступ жив. Риски не растут.

## Q-3.2 — Доступ к версии рецепта

**① Состояние кода.** 0072 добавляет `recipe_purchases.recipe_version_id` (nullable, FK SET NULL): при покупке фиксируется последняя версия на момент webhook (`webhook route.ts:386-401`). НО Access Resolver (src/lib/recipes/access-resolver.ts:149-152) при `full/PURCHASED` отдаёт **весь контент корня** без ограничения по купленной версии; `recipeVersionId` возвращается в meta и больше нигде не используется. PATCH корня автором не блокируется для published-рецептов (recipes/[id]/route.ts:318-421), publish создаёт новую версию, статус остаётся published.

**② Фактическое поведение.** Фактическая модель = «entitlement привязан к рецепту-корню»: покупатель после новой публикации автора автоматически получает и новый контент (нужно только заново открыть рецепт). Колонка `recipe_version_id` — информационная.

**③ Риск.** Расхождение между комментарием в коде («Q-3.2 default: доступ на зафиксированную версию») и фактическим поведением. Автор может изменить состав уже купленного рецепта — покупатель увидит изменения. Обратная сторона: «версионная» модель требует механики доступа к старым снапшотам (их отдача покупателю, pricing обновлений).

**④ Варианты.**
- **A:** покупка закрепляет конкретную версию; новые версии — по отдельному предложению/обновлению (честно к ожиданиям «я купил то, что видел», но заметная доработка: выдача контента версии в GET, UI «доступна новая версия», политика ретроактивности).
- **B:** покупка открывает весь рецепт, включая будущие версии (текущая фактическая модель; минимум доработки — только привести комментарии/документы в соответствие).

**⑤ Рекомендация:** вариант B (легализовать текущее поведение): посильнее коммуникация в UI («доступ включает будущие обновления рецепта») — но это продуктовая формулировка, остаётся за владельцем.

**⑥ Затронутое при выборе A:** access-resolver (фильтрация контента по версии), GET recipes/[id] и marketplace/[id] (отдача снапшота), entitlement UI, e2e recipe-purchase-flow.

**⑦ Тесты:** текущие контракт-тесты E2E покупок не зависят от выбора; при A потребуется новая ветка тестов.

**⑧ Как есть:** покупатели получают обновления автоматически; риск несоответствия ожиданиям минимальный, документального соответствия добьёмся правкой комментариев.

## Q-4 — Права роли SUPPLIER

**① Состояние кода.** Поставщик — обычный authenticated: покупка рецепта доступна ему на общих основаниях (purchase route не ограничивает роль покупателя). Продажа собственных товаров — через /api/supplier/products (склад поставщика, owner_id = поставщик). Доступ к складским данным кондитера: RLS inventory_items (owner_id = auth.uid()) — чужие остатки не читаются. Производственные данные (production cards/batches) — серверные API с проверкой владения.

**② Фактическое поведение.** Поставщик может купить чужой рецепт как обычный покупатель; не может продавать чужие рецепты (создание оффера требует RECIPE_DEVELOPER — marketplace/route.ts:206); склад и производство других — изолированы RLS/проверками.

**③ Риск.** Низкий: разделение уже реализовано. Спорное — может ли SUPPLIER стать RECIPE_DEVELOPER и продавать СВОИ рецепты — это вопрос выдачи второй роли, решается администратором вручную.

**④ Матрица (фактическая).**

| Действие | Доступно SUPPLIER? |
|---|---|
| Покупка рецепта как обычный покупатель | Да |
| Продажа собственных товаров (склад поставщика) | Да |
| Продажа чужих рецептов | Нет (нужна RECIPE_DEVELOPER) |
| Чтение чужого склада / остатков | Нет (RLS owner) |
| Доступ к производственным данным кондитера | Нет (владение) |
| Управление заказами кондитера | Нет |

**⑤ Рекомендация:** сохранить как есть; автоматического расширения прав не делать.

**⑥⑦⑧:** изменений не требует; рисков при статус-кво не выявлено.

## Q-6 — Права роли CONFECTIONER (продажа собственных рецептов)

**① Состояние кода.** Создание оффера маркетплейса требует ровно роли RECIPE_DEVELOPER (requireRole, marketplace POST). Кондитер НЕ может продавать рецепты, пока администратор не выдаст RECIPE_DEVELOPER. Модерация: публикация — через publish (RECIPE_MODERATION_REQUIRED=true → pending_review + moderator approve; по умолчанию — прямая публикация, «Период Завис-2»).

**② Фактическое поведение.** Кондитер может создать черновик рецепта (recipes API не ограничен ролью), но не может создать оффер и продавать.

**③ Риск.** Продуктовое ограничение: кондитер с собственными рецептами не может их монетизировать без ручной выдачи роли. Технических дыр нет: проверка роли серверная (user_roles), самоповышение заблокировано RLS (изоляционная проба «A самоповышение до ADMIN → 42501», обобщается на INSERT любой роли: CHECK is_platform_admin()).

**④ Матрица (фактическая).**

| Действие | CONFECTIONER сегодня |
|---|---|
| Создание собственных рецептов (draft) | Да |
| Публикация после модерации/без (Завис-2) | Да (publish) |
| Продажа собственных рецептов (оффер) | Нет — только с RECIPE_DEVELOPER |
| Продажа чужих рецептов | Нет |
| Производственные данные (карты/партии) | Да, свои |
| Чтение рецептов покупателей | Нет (свои + published) |

**⑤ Рекомендация:** разрешить кондитеру продажу СВОИХ рецептов (либо второй ролью RECIPE_DEVELOPER по заявке, либо расширить requireRole на CONFECTIONER) — при обязательном сохранении: покупка чужого ≠ продажа чужого; публикация оффера только после публикации корня (уже обеспечено PATCH-гейтом и покупкой).

**⑥ Затронутое при утверждении:** marketplace/route.ts (requireRole), возможно роль-гварды и UI кабинета; модерация не меняется.

**⑦ Тесты:** moderation-bypass.test.ts (4 контракта) — не затрагиваются.

**⑧ Как есть:** кондитеры не продают рецепты; спрос удовлетворяется ручной выдачей роли админом.

## Q-7 — RLS: спорные политики `USING(true)`

**① Состояние (актуальная БД, реестр r03v-rls-registry-2026-11-09T21-31-53.json).** 367 политик; `USING(true)` — 25; `WITH CHECK(true)` — 4. Из 25: **ровно 10** — операционные таблицы 0053/0054 (domain_events, ops_tasks, purchase_drafts, purchase_draft_items, recipe_ingredients, confectioner_capacity, capacity_reservations, order_production, order_production_checklist, order_media) — предмет SECURITY-RECIPE-01; остальные 15 — публичные каталог-SELECT (products*, builder*, holidays, permissions, uploads и т.п.), WHERE-риск которых — раскрытие каталога, что и задумано. Все 4 `WITH CHECK(true)` нейтрализованы GRANT-уровнем (INSERT-гранта anon/authenticated нет — проба «C INSERT fraud_log → 42501»).

**② Фактическое поведение.** Прямое PostgREST-чтение 10 операционных таблиц под `authenticated` возвращает ВСЕ строки (без owner-фильтра). GRANT SELECT есть (0002 blanket). Клиентского кода, читающего их напрямую, нет (аудит SECURITY-RECIPE-01 §2 перепроверен grep'ом — совпадает).

**③ Риск.** Латентный enrichment: любой будущий клиентский `.from("ops_tasks")` молча получит чужие строки. Ранее заявленное расхождение «7 vs 10»: 7 — старая оценка по одному файлу 0053 (5 шт.) + часть 0054; точное фактическое число из БД — **10** (подтверждено и grep по миграциям, и выгрузкой pg_policies).

**④ Варианты.**
- **A:** сузить ровно 10 политик по SECURITY_RECIPE_01_PROPOSAL.md (миграция 0073 зарезервирована; готовые USING-выражения, серверные пути не затронуты — все чтения идут через getPool()/supabaseAdmin).
- **B:** оставить как есть с записанным риском (поверхность атаки ограничена отсутствием клиентских чтений).

**⑤ Рекомендация:** вариант A — предложение готово, риски сужения минимальны (документ §4), откат тривиален.

**⑥ Затронутое:** только RLS SELECT этих 10 таблиц; ни один API-маршрут поведение не меняет (сервер читает BYPASSRLS-путями).

**⑦ Тесты:** после применения — негатив-пробы под authenticated (пустые наборы), прогон prodpath-харнесса.

**⑧ Как есть:** риск остаётся латентным; при добавлении клиентских чтений — мгновенно актуализируется.

## Q-10 — Склад: DB-уровневая защита количества

**① Состояние кода.** Полная цепочка уже реализована и независимо проверена на disposable PG18 (r03v-privilege-matrix-*.json, 18/18): REVOKE I/U/D на inventory_items/stock_movements (0077); единственные атомарные пути — RPC `apply_inventory_movement_atomic` (0048: FOR UPDATE → guard OUT<0 → UPDATE остатка → INSERT движения в одной транзакции) и `apply_inventory_write_off_batch` (0071: реестр-первым, UNIQUE-ключи (owner,order,signature)/batch_id/idempotency_key, FOR UPDATE на каждую позицию, unit-mismatch, forbidden_item); EXECUTE только service_role; CHECK quantity ≥ 0 (0077); API-роуты не имеют quantity в whitelist обновлений.

**② Фактическое поведение.** Прямой UPDATE количества из-под authenticated → 42501; отрицательный остаток через RPC → `insufficient` (без изменения); прямой отрицательный UPDATE даже от service_role → CHECK 23514; повтор с тем же idempotency_key → replay без второго движения; конкурентный двойной OUT → ровно один успех; остаток и журнал согласованы (реплей журнала = quantity).

**③ Риск.** Остаточный: service_role-код (сервер) технически может писать в обход RPC (это свойство любой сервисной роли); защита — ревью + тесты. Мелкий пробел: `search_products` остаётся EXECUTE-доступным клиенту (нужен UI-поиску) — к остаткам не обращается.

**④ Варианты.** A: оставить как есть (реализованное состояние уже соответствует требуемой архитектуре «запрет прямого UPDATE + единая атомарная RPC + журнал + idempotency + транзакционность + ownership + запрет отрицательного остатка»). B: добавить триггер-иммутабельность журнала (запрет UPDATE/DELETE inventory_movements даже для service_role) — усиление за счёт осложнения легитимных административных исправлений.

**⑤ Рекомендация:** вариант A — критерий завершения §3.5 закрыт на уровне БД-доказательств; триггер не требуется («не без необходимости не вводить триггер»).

**⑥ Затронутое:** ничего (статус-кво); при B — новый триггер + миграция + пересмотр cleanup/backup путей.

**⑦ Тесты:** inventory-quantity-via-movement.test.ts, write-off.idempotency.test.ts, prodpath GRANT-assertions, независимые 18/18 проб.

**⑧ Как есть:** защита сохраняется; единственная долгосрочная рекомендация — не вводить новые клиентские GRANT на складские таблицы без повторного гейта.
