# Z-v27 — RECIPE VERSIONING RISK (исторические заказы и версии рецептов)

Дата: 2026-11-11 · HEAD `664e1e5` · классификация: **P2 — целостность бизнес-процесса**
(повышено с P3/INFO Z-v26 на основании новых доказательств; до P1/P0 не дотягивает:
повреждения склада, цен или списаний нет)

---

## 1. Фактическая модель (проверено по коду, не по отчётам)

### 1.1. Что НЕ снапшотится

`order_items` хранит только коммерческий снапшот: `product_title`, `unit_price`,
`quantity`, `selected_attributes` — **ни recipe_id, ни ингредиентов, ни их количеств**.
Разбор заказа (`computeOrderBreakdown`, `checkOrderAcceptance`) каждый раз читает
ТЕКУЩИЙ рецепт: `order_items → products.recipe_id → recipe_ingredients`.
Таблица `recipe_versions` существует (миграция 0067-поколение), но **0 строк** —
не используется товарным путём.

### 1.2. Кто читает ТЕКУЩИЙ рецепт для СТАРОГО заказа

| Функция | Маршрут | Эффект правки рецепта |
|---|---|---|
| `checkOrderAcceptance` | `POST /api/orders/[id]/accept`, `GET /api/orders/[id]/acceptance-check`, `GET /api/ops/confectioner-today` | повторный расчёт потребности → может заблокировать accept |
| `computeOrderBreakdown` | `GET /api/orders/[id]/breakdown`, `POST /api/orders/[id]/purchase-draft` | состав/дефицит/закупка меняются |

### 1.3. Что от рецепта НЕ зависит (безопасно)

- **Ручное списание (order-путь, 0048/0049)**: количества вводит кондитер; идемпотентность
  по (owner, order, signature); рецепт не читается.
- **Партийное производство (RECIPE-02/05, 0070/0071)**: нормы фиксируются в
  `recipe_production_card_versions.snapshot`; партии ссылаются на `card_version_id` —
  версионирование ЕСТЬ.
- Цены/итоги заказа: снапшот в `order_items` — не меняются.

## 2. Доказательное воспроизведение (disposable PG 18.4, `agent-ctx/zv27/gate-scenarios.mjs`, сценарии I/M)

| Шаг | Результат |
|---|---|
| Заказ с рецептом (Ягоды 250 г) | разбор: required=250 |
| Правка рецепта 250→500 | разбор СТАРОГО заказа: **required=500** (I2) |
| Склад 250 г → `checkOrderAcceptance` старого заказа | **canAccept=false, canProduce=false, дефицит −250** → accept вернёт 409 ORDER_NOT_FEASIBLE (M1) |
| Откат рецепта | приемлемость восстановлена, заказ не повреждён (M3) |

## 3. Оценка риска (по фактическому влиянию)

| Сценарий | Влияние | Серьёзность |
|---|---|---|
| Правка рецепта после ОПЛАТЫ, до accept | оплаченный заказ нельзя принять (409); спасается откатом правки или пополнением склада; деньги/данные не теряются, но бизнес-процесс ломается | **P2** |
| Правка рецепта после accept (CONFIRMED+) | меняются разбор/потребность/закупка у истории; списания уже совершённые не переписываются; риск — неверная закупка и аналитика | **P2** |
| Правка ДО оформления заказа | корректное поведение (расчёт по актуальной рецептуре) | — |

## 4. Предпочтительная модель решения (для решения владельца; НЕ внедрялось)

1. **Минимальная (рекомендуется первой):** снапшот потребности при checkout —
   зафиксировать ingredients (name, qty, unit) в `orders.metadata.acceptance_snapshot`
   (jsonb, БЕЗ миграции: metadata уже существует). Accept/breakdown читают снапшот,
   если он есть; расчёт «в живую» остаётся для админ-просмотра актуального состава.
   Обратно совместимо: старые заказы (без снапшота) ведут себя как сейчас.
2. **Средняя:** включить механизм `recipe_versions` (публикация рецепта создаёт версию;
   `products.recipe_version_id` фиксирует версию; порядок: миграция + бэкфилл).
3. **Полная:** immutable recipe cards с card_version для товарного пути (как у партий).

## 5. План тестирования решения (когда будет одобрено)

1. Checkout товара → в order появляется снапшот потребности.
2. Правка рецепта → accept/breakdown СТАРОГО заказа неизменны.
3. Новый заказ после правки — по новой рецептуре.
4. Конкурентные заказы на разных версиях рецепта.
5. Полный регресс: lifecycle 81/81, checkout-idempotency, p11, vitest.

## 6. Временные меры до решения владельца (без изменения кода)

- Не редактировать рецептуры товаров, по которым есть оплаченные/принятые заказы
  (организационная мера — на усмотрение владельца).
- При блокировке accept (409) у оплаченного заказа — вернуть правку рецепта или
  пополнить склад до покрытия новой потребности; заказ не теряется.
