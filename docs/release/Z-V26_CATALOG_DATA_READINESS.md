## Формат данных, которых не хватает (§5.1)

Для каждого товара владельцу нужно предоставить (ничего из этого не придумывается системой):
1. **Рецепт**: название + ингредиенты (наименование, количество на 1 единицу товара, единица: г/мл/шт/дес) + опционально prep/cook минуты. Создание — через UI «Рецепты» (или recipes + recipe_ingredients).
2. **Привязка**: `products.recipe_id` на карточке товара (UI карточки товара).
3. **Время производства**: `products.production_time_hours` (или prep/cook в рецепте).
4. **Склад**: позиции `inventory_items` с ТОЧНЫМИ именами ингредиентов рецепта (либо связать `recipe_ingredients.inventory_item_id`), количество ≥ потребности, `is_active=true`.
5. **Закупка (если дефицит)**: черновик закупки с `expected_eta` РАНЬШЕ безопасного старта производства (deadline 18:00 − производственное время).
6. **Мощность** (опционально): `confectioner_capacity` — иначе глобальные дефолты 9:00–18:00 (480 мин/день).

Последствия отсутствия: без рецепта — `RECIPE_MISSING` (блок); без склада/ETA — `LOW_STOCK`/`PURCHASE_ETA_MISSING` (блок); ETA после безопасного старта — `PURCHASE_ETA_AFTER_DEADLINE` (блок).

## Как проверить закрытие (после ввода данных владельцем)

1. `node scripts/verify/p11-hardening-verify.mjs` → ожидание 17/17 (сейчас 12/17 из-за каскада F1).
2. HTTP checkout товарной позиции → 200/201 (сейчас 422, причины точны — см. Z-V26_CHECKOUT_EVIDENCE.md).

## Праймер для товара №1 (минимальный путь к первому READY)

Данные, которые должен подтвердить владелец (система не придумывает): фактическое наличие и количество «Ягоды» на складе кондитера «Сахарная печать» (-0101) ИЛИ реальная дата поставки для черновика закупки `eaf5ae25` (в нём уже 3 позиции «Ягоды»).
