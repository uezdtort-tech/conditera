# Z-v27 — OWNER ACTIONS

Только конкретные действия владельца. Публикация (push/merge/deploy) остаётся ЗАПРЕЩЕНА
до отдельного решения владельца.

## 1. Данные товара №1 «Свадебный торт «Ягодный бархат»» — разблокирует первый товарный заказ

- **Что требуется** — ОДНО из двух по ингредиенту «Ягоды»:
  - (а) фактический остаток на складе кондитера «Сахарная печать» (`…-0101`): создать/пополнить
    позицию `inventory_items` с ТОЧНЫМ именем «Ягоды», единица «г», количество ≥ 250 г на торт
    (учтите планируемое число заказов в день); или
  - (б) реальная дата поставки для существующего черновика закупки `eaf5ae25-2fb9-4496-80ec-6e2573d9fcd7`:
    заполнить `expected_eta` (UI «Закупки»), дата должна наступать РАНЬШЕ безопасного старта
    производства (дедлайн 18:00 − время производства).
- **Зачем**: снимает единственные блокеры товара `LOW_STOCK` + `PURCHASE_ETA_MISSING`.
- **Кто**: владелец (только фактические данные — система не придумывает остатки и ETA).
- **Как проверить**: `node scripts/verify/p11-hardening-verify.mjs` (17/17) → HTTP checkout → 200/201 →
  `bun agent-ctx/zv27/catalog-map.mjs` (товар №1 = GATE-PASS).
- **Что заблокировано до этого**: любой товарный checkout (422). Custom-позиции конструктора работают.
- **Опционально**: `production_time_hours` в карточке товара (сейчас warning MISSING_PRODUCT_DATA) —
  влияет на точность DEADLINE_TOO_CLOSE/CAPACITY расчётов, НЕ блокирует.

## 2. Рецепты для остальных 11 товаров

- **Что требуется**: для каждого товара, который должен продаваться: рецепт (ингредиенты: имя,
  норма на 1 единицу, единица г/мл/шт/дес) + привязка `recipe_id` на карточке товара
  (+ желательно `production_time_hours`). Существующие 4 рецепта можно привязывать ТОЛЬКО если
  они соответствуют фактической рецептуре.
- **Зачем**: без рецепта гейт блокирует (`RECIPE_MISSING`) — осознанный контракт.
- **Проверка**: после привязки — catalog-map + checkout каждого товара.

## 3. Склады кондитеров «Сладкая уездная» (-0102) и «Кондитерская Купеческая» (-0103)

- **Что требуется**: позиции склада (сейчас 0 строк у обоих) — у их товаров (№4,5,6,7,8,10,11,12)
  нечего списывать даже при наличии рецептов.
- **Проверка**: разбор заказа не должен показывать no_stock.

## 4. Мощность для товара №7 «3D-торт «Коровка»» (12 ч)

- **Что требуется**: `confectioner_capacity` для кондитера с окном ≥ 720 мин/день ИЛИ пересмотр
  `production_time_hours`. Сейчас: дефолт 9:00–18:00 = 480 мин < 720 → после привязки рецепта
  заказ всё равно блокировался бы `CAPACITY_EXCEEDED`.
- **Проверка**: catalog-map для №7: blocking codes без CAPACITY_EXCEEDED.

## 5. YooKassa sandbox

- **Что требуется**: `YOOKASSA_SHOP_ID` + `YOOKASSA_SECRET_KEY` (sandbox-пара) в окружение
  (файл `.env.local`, секреты в чат НЕ вставлять).
- **Проверка**: sandbox-платёж на тестовом заказе → webhook `payment.succeeded` → статус заказа.
  Реальные платежи не выполнять до решения о запуске.

## 6. OAuth Yandex ID

- **Что требуется**: зарегистрировать приложение в Яндекс ID, получить `YANDEX_CLIENT_ID`/`SECRET`,
  указать callback, внести в окружение. (VK ID не реализован — скрыть кнопку или задача.)
- **Проверка**: кнопка «Я Яндекс» → redirect → callback → сессия.

## 7. Email/SMTP и Telegram (не блокер)

- **Что требуется**: `SMTP_HOST/PORT/USER/PASS` и опционально `TELEGRAM_BOT_TOKEN`.
- **Проверка**: регистрация нового пользователя получает письмо; заказ доставляет уведомление.

## 8. Решение по версионированию рецептов (P2, см. Z-V27_RECIPE_VERSIONING_RISK.md)

- **Что требуется**: выбрать вариант снапшота потребности заказа
  (рекомендация — вариант 1: `orders.metadata.acceptance_snapshot`, без миграции).
- **Зачем**: правка рецепта сейчас может сделать ОПЛАЧЕННЫЙ заказ неприемлемым (409) и меняет
  разбор/закупки исторических заказов.
- **Временная мера до решения**: не редактировать рецептуры товаров с активными заказами.

## 9. n8n workflow engine (опционально, не блокер витрины)

- **Что требуется**: развернуть n8n (Docker), импортировать минимум: `order.created → уведомление`,
  `order.paid → задача кондитеру`. Сейчас работает только webhook-receiver (:5678, события копятся).

## Что владельцу делать НЕ нужно (закрыто Z-v24–Z-v27)

- Конфликт миграции 0062, fake-success раннеров, advisory lock, дубликат-гейт — закрыты и верифицированы.
- **НОВОЕ (Z-v27)**: fail-open checkout-гейта при неизвестной единице склада — исправлено
  (`INVENTORY_UNIT_MISMATCH`, блокирующий), покрыто тестами, полный регресс зелёный.
