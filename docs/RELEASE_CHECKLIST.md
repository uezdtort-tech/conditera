# RELEASE CHECKLIST — production Conditera

Релиз разрешён только после фактического выполнения каждого пункта на одном и том же актуальном SHA. Успешная сборка, отдельный health endpoint или CI на PostgreSQL 15 не являются доказательством production readiness.

## 1. Каноническая архитектура и база

- [ ] Целевая база — чистый PostgreSQL 17.12 в новом постоянном volume.
- [ ] Подтверждено решение владельца: прежние базы пустые, перенос/слияние пользовательских данных не требуется.
- [ ] Один контейнер `supabase-runtime` содержит PostgreSQL 17, GoTrue, PostgREST, Realtime, Storage, Postgres Meta, Imgproxy, Kong и Edge Runtime.
- [ ] Next.js, Auth, REST, Realtime, Storage и производственные API используют одну каноническую базу.
- [ ] Production seeds выключены: `SEED_MODE=none`.
- [ ] Старые PG15/PG18 кластеры не используются как целевая БД; старые volumes не удаляются автоматически.

## 2. Миграции и схема

- [ ] На чистой PG17 применены все SQL-миграции из `supabase/migrations`.
- [ ] `public.schema_migrations` точно совпадает со списком SQL-файлов репозитория: нет пропущенных и неожиданных записей.
- [ ] Повторный `bun run db:setup` проходит без ошибок и не меняет migration ledger.
- [ ] Проверены критические таблицы, индексы, функции, триггеры, grants и RLS.
- [ ] Проверены роли приложения и резервного копирования: `conditera_app` и `conditera_backup`.
- [ ] Роль `conditera_backup` имеет только необходимые read-only права, `pg_read_all_data` и `BYPASSRLS`; она реально выполняет pg_dump всех нужных схем.

## 3. CI и сборка

- [ ] Все GitHub Actions на текущем SHA завершились успешно: lint, typecheck, unit/integration tests, migration regression, PG17 Compose, Supabase runtime POC, E2E.
- [ ] Полный E2E выполнен именно на PostgreSQL 17, а не только на PG15/PGlite.
- [ ] Production Docker image собран и запущен против PG17.
- [ ] `GET /api/health` возвращает 200 и актуальный SHA.
- [ ] Playwright Chromium и mobile-chrome прошли без необработанных JS-ошибок.
- [ ] Проверены публичные страницы, каталог, карточки, login/register, checkout, кабинеты, конструктор и основные формы.
- [ ] Проверены HTTP-статусы страниц/API: тесты не допускают 500 как приемлемый fallback.

## 4. Полный бизнес-путь

- [ ] Покупатель регистрируется и подтверждает необходимые согласия.
- [ ] Вход, выход, refresh, revoke и конкурентный вход проверены; при конфликте ровно один запрос получает 200, проигравший — 409.
- [ ] OAuth Yandex ID и VK ID проверены с реальными credentials и корректными callback/redirect URI.
- [ ] Покупатель создаёт обычный заказ и индивидуальный запрос на торт.
- [ ] Кондитер видит запрос, отвечает, прикрепляет медиа и отправляет предложение.
- [ ] Покупатель принимает предложение; заказ создаётся в той же канонической БД.
- [ ] Оплата через тестовый контур YooKassa создаёт платёж и escrow; повтор webhook идемпотентен.
- [ ] Частичный и полный возвраты проверены, включая конкурентные запросы и повторную доставку webhook.
- [ ] Кондитер принимает заказ, выбирает рецепт, проверяет склад, списывает ингредиенты и проходит стадии производства.
- [ ] Проверены фото готового изделия, передача курьеру/самовывоз, подтверждение получения и спор.
- [ ] Чат покупателя, кондитера и поддержки сохраняет историю и изолирует чужие заказы/пользователей.
- [ ] Проверены роли, RLS, запрет передачи аккаунта, отзыв сессий и ограничения одновременных устройств.

## 5. Резервное копирование и восстановление

- [ ] Создан непустой архив PG17 через `conditera_backup`.
- [ ] `gzip -t` подтверждает целостность архива.
- [ ] Архив восстановлен в отдельную чистую shadow-БД; сверены критические таблицы и количество строк.
- [ ] Storage files и метаданные резервируются отдельно; проверены хеши/размеры и восстановление файлов.
- [ ] Backup volume и копия вне локального ПК настроены до приёма реальных пользовательских данных.
- [ ] Проверены расписание, retention, алерты о неудачном backup и заполнении диска.

## 6. Безопасность

- [ ] Все production secrets сгенерированы локально и не находятся в Git, CI-логах или открытом чате.
- [ ] `NODE_ENV=production`; отсутствуют dev auth/payment stubs и небезопасные fallback-значения.
- [ ] Проверены CSRF, rate limits, auth/session rotation, account/device controls, webhook signatures и idempotency.
- [ ] Проверены CSP, security headers, CORS, cookie flags, no-store для чувствительных ответов.
- [ ] PostgreSQL, Redis, Supabase внутренние API, Kong admin, n8n UI и Docker API не доступны из интернета.
- [ ] Caddy — единственная публичная точка входа; TLS сертификат действителен.
- [ ] Нет критических/высоких уязвимостей в зависимостях и контейнерных образах.

## 7. Адаптивность, производительность и SEO

- [ ] Mobile Playwright прошёл на всех основных публичных маршрутах без горизонтального переполнения.
- [ ] Проверены реальные узкие экраны и основные пользовательские действия на мобильном устройстве.
- [ ] Главная и каталог укладываются в согласованные performance budgets; нет критических блокирующих ресурсов.
- [ ] Изображения оптимизированы, responsive sizes заданы, тяжёлые медиа не блокируют первый экран.
- [ ] `robots.txt`, `sitemap.xml`, canonical, title/description, Open Graph и структурированные данные проверены.
- [ ] Закрытые/служебные страницы имеют корректный noindex.
- [ ] Нет дублирующихся canonical URL, индексируемых query-параметров и несуществующих страниц.

## 8. Реальные интеграции

- [ ] YooKassa: реальные merchant credentials, тестовая оплата, webhook и возврат.
- [ ] SMTP: подтверждена доставка письма с корректным sender/domain.
- [ ] Telegram: webhook зарегистрирован, secret token проверяется, тестовое уведомление получено.
- [ ] Yandex ID и VK ID: реальные приложения, секреты/ключи и redirect URI настроены.
- [ ] Все включённые Edge Functions реализованы и проверены; ни один обязательный вызов не возвращает `501 not_implemented`.
- [ ] Неиспользуемые функции явно отключены и не вызываются критическими бизнес-процессами.

## 9. Локальный production deployment

- [ ] На целевом Windows ПК доступен Docker Desktop (Linux containers/WSL2), достаточно места и памяти.
- [ ] Проверены Windows Firewall, NAT/port forwarding, DNS домена и публичная доступность.
- [ ] Секреты подготовлены через `bash scripts/prepare-production-env.sh`.
- [ ] `bash scripts/deploy-single-container.sh --config` проходит без ошибок.
- [ ] Первый старт выполнен на новом PG17 volume с `SEED_MODE=none`.
- [ ] После старта проверены все процессы, health endpoints, Auth, REST, Realtime, Storage и web.
- [ ] Проверен перезапуск контейнеров и Docker Desktop, перезагрузка Windows и восстановление после потери сети.
- [ ] Публичный домен открывается по HTTPS; HTTP перенаправляется на HTTPS.
- [ ] Не используется исторический удалённый VPS workflow.

## 10. Подтверждение

- [ ] Все пункты выше подтверждены командами, тестами, реальными URL или артефактами.
- [ ] Сохранены SHA релизного кода, образа и результаты CI.
- [ ] Назначен ответственный за мониторинг и откат.
- [ ] Настроен мониторинг 5xx, health, свободного места, ошибок оплаты, очередей и backup.
- [ ] Только после этого статус можно изменить на READY.
