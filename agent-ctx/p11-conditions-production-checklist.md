# P1.1 — Production Checklist: условия C1–C7 (READY WITH CONDITIONS)

> Статус P1.1: **READY WITH CONDITIONS** (зафиксировано в ТЗ P1.2).
> Условия НЕ блокируют разработку P2. Каждое закрывается точечно при
> подключении соответствующей production-инфраструктуры.
> Отсутствие production credentials при локальной разработке не задерживает P2.

---

## C1. Реальная оплата

**Когда:** подключение production payment provider.

Чек-лист проверки (минимум):
- [ ] `create payment → redirect → webhook → paid` — полный цикл на реальном провайдере
- [ ] повторный webhook (дубликат) не создаёт второго зачисления/уведомления
- [ ] refund: создание возврата, повторный запрос возврата → идемпотентно
- [ ] idempotency: повторный `create payment` для одного заказа не создаёт второй платёж
- [ ] `payment.amount = orders.total` (сверка при подтверждении; расхождение → amount_mismatch)
- [ ] повторное оплата после отмены платежа — новое поколение Idempotence-Key
- [ ] **dev/test stub не работает в production** (реализовано в P1.1: production + незавершённый шлюз → 503 до создания заказа; unit-покрытие `payment-prod-guard.test.ts`)

## C2. Реальные уведомления

**Когда:** подключение n8n / SMTP / push.

Проверить доставку фактическую (не только DB-запись) минимум для:
- [ ] новый заказ (`ORDER_CREATED`)
- [ ] новое сообщение (`NEW_MESSAGE`)
- [ ] заказ готов (`ORDER_READY`)
- [ ] проблема с заказом (тикет)
- [ ] возврат (`REFUND_PROCESSED`)

Правило: **DB notification ≠ фактическая доставка** — два уровня проверки.
In-app канал уже фильтруется в колоколе (`channel=in_app`, P1.1 dedup по
`metadata->>'dedup_key'`); push/email — проверять при подключении каналов.

## C3. n8n

**Когда:** включение реальных n8n workflow.

- [ ] `order.created` → n8n → action (реальный вызов)
- [ ] `order.paid` → n8n → action
- [ ] `order.status_changed` → n8n → action
- [ ] **повторное событие не создаёт повторное действие** (dedup_key в
      domain_events + ON CONFLICT DO NOTHING реализованы в P1.1; на стороне
      n8n — включить идемпотентность воркфлоу)

## C4. Chat abuse protection (direct chat)

**Когда:** открытие direct-чата между пользователями (не order-чат).

- [ ] authorization (membership — реализовано в P1.1 для order-комнат)
- [ ] consent на прямой контакт
- [ ] rate limit на сообщения
- [ ] невозможность массовой рассылки
- [ ] невозможность писать пользователю без допустимого основания (order/заказ как основание)

Не строить сложную модерационную систему.

## C5. Order API data exposure

**Когда:** подключение роли COURIER/SUPPORT к рабочим процессам.

- [ ] `/api/orders/[id]`: courier/support получают только необходимый набор данных
- [ ] payment data скрыта от courier
- [ ] внутренние/административные поля скрыты
- [ ] чужие персональные данные скрыты

Принцип: **роль получает только необходимый набор данных**.
P1.1 закрыл запись (PATCH: курьер двигает только свои delivery-заказы);
чтение сузить при подключении роли.

## C6. Event failure (event created → downstream unavailable)

**Когда:** первая реальная интеграция с внешним обработчиком событий.

Минимально обеспечить:
- [ ] событие не теряется незаметно (domain_events сохранён до отправки)
- [ ] повторная обработка безопасна (dedup_key, идемпотентные consumers)
- [ ] ошибка видна администратору/системе (лог/алерт)

Не строить Kafka/DLQ-инфраструктуру. Retry-механизм отправки — бэклог.

## C7. P1.2 не превращается в новый проект

- [ ] условия закрываются точечно по мере подключения инфраструктуры
- [ ] P2 не задерживается из-за отсутствия production credentials
