# Часть I. Аудит по файлам

## 0. Главный вывод (одним абзацем)

Платёжный контур **работает только по одному «счастливому» пути** (checkout → webhook → escrow-cron) и только при `NODE_ENV != production`. В нём **перемешаны рубли и копейки** (два маршрута создания заказа считают одну и ту же цену `products.price` в разных единицах — расхождение 100×), **два webhook-обработчика** дублируют друг друга, **три несогласованных механизма выплат**, идемпотентность построена на проверках статусов вместо уникальных ключей, и **нигде нет двойной бухгалтерской записи (ledger)** — баланс кондитера — это одно число в таблице `confectioners`, которое три разных флоу инкрементируют/декрементируют неатомарно. В текущем виде контур нельзя выпускать на реальные деньги.

## 1. `POST /api/checkout` (`src/app/api/checkout/route.ts`)

**Что хорошо:**
- Цены пересчитываются на сервере из БД (снапшот в `order_items`), статус товара проверяется.
- Сумма в YooKassa: `(total / 100).toFixed(2)` — корректная конвертация копеек → рубли.
- Auth через `getSession()` (Supabase SSR) — канонический стек по docs/AUTH.md.

**Критично:**

| # | Проблема | Детали |
|---|----------|--------|
| 1.1 | 🔴 **Idempotence-Key недетерминирован** | `const idempotenceKey = \`${order.id}-${Date.now()}\`` — двойной клик «Оплатить» = **два реальных платежа** по одному заказу. В `src/lib/yookassa.ts` уже есть детерминированный `idempotenceKeyFor("create", orderId)`, но checkout делает собственный inline `fetch`, игнорируя библиотеку. |
| 1.2 | 🔴 **Нет валидации `quantity`** | В отличие от `POST /api/orders` (там 1..999), checkout принимает любое число: `quantity: 0` → `total = 0` → бесплатный заказ; отрицательное → отрицательный total. Zod-схема не применяется. |
| 1.3 | 🔴 **Нет транзакции / компенсации неполные** | 6 последовательных операций: order → order_items → YooKassa → payments → cart delete → notification. При падении order_items заказ удаляется, но при падении payments — осиротевший order без payment. Ручной `delete` вместо транзакции. |
| 1.4 | 🟠 **Корзина очищается до оплаты** | `cart_items` удаляются в момент создания платежа. Не оплатил → корзина потеряна. |
| 1.5 | 🟠 **Дублирование провайдерской логики** | Собственный inline `fetch` + собственная конвертация вместо `createPayment()` из `@/lib/yookassa`. Именно это и породило баг 1.1. |
| 1.6 | 🟠 **`confectioner_id` только от первого товара** | Мультикондитерская корзина → все деньги уходят одному кондитеру. Комиссия второго — мимо. |
| 1.7 | 🟡 **Утечка деталей** | `{ error: "Внутренняя ошибка", detail: (error as Error).message }` — может уйти сообщение БД/провайдера. |

## 2. `POST /api/orders` (`src/app/api/orders/route.ts`)

**Что хорошо:** anti-fraud 5 заказов/час; quantity 1..999; серверная валидация промокода (`validatePromoCode`); атомарное списание бонусов (`redeemPoints` → RPC `deduct_bonus_balance` c FOR UPDATE + защита от double-spend); снапшот тарифа/комиссии в заказ.

**Критично:**

| # | Проблема | Детали |
|---|----------|--------|
| 2.1 | 🔴 **Разнобой единиц: копейки vs рубли** | `products.price INTEGER -- в копейках` (миграция 0002). Этот маршрут считает `itemsTotal = price * qty` **и трактует как рубли**: `deliveryCost` клампится 0..5000 (рубли), промо-скидка `discountRub` (рубли), `finalTotal = itemsTotal + deliveryCost − скидки`. Итог: `order.total` — **смесь копеек и рублей** (на практике ≈ 100× завышение товарной части). Checkout трактует тот же `products.price` как копейки. Два маршрута создания заказа несовместимы на 2 порядка. |
| 2.2 | 🔴 **`POST /api/payment/create` отправляет `order.total` как рубли** | `createPayment({ amount: Number(order.total) })` → `value: amount.toFixed(2)` **в рублях**. Если total в копейках — пользователь заплатит **в 100 раз больше** (или провайдер отклонит). Если через checkout — ок. Поведение зависит от того, каким маршрутом создан заказ. |
| 2.3 | 🟠 **order_items могут не создаться** | `if (itemsErr) { console.error; /* не откатываем */ }` — заказ без позиций валиден для системы. |
| 2.4 | 🟠 **TOCTOU на промокоде** | `select used_count` → `update used_count+1` — параллельные заказы используют один промокод сверх лимита. |
| 2.5 | 🟠 **Коллизия номера заказа** | `UK-YYYY-` + `Date.now().slice(-6)` — при двух заказах в одну миллисекунду → unique violation, заказ теряется. |
| 2.6 | 🟠 **Бонус-дисконт финализирован до валидации** | `bonusDiscountRub = requested` до вызова `redeemPoints` (тот бросает исключение → заказ отменился — ок, но `total` уже записан уменьшенным; логика держится на порядке вызовов). |
| 2.7 | 🟡 **Комиссия — вторая копия таблицы тарифов** | Локальная `TARIFF_RATES`: `BASIC: 0.15`, а в `finance.ts TARIFFS`: `BASIC: 0.12`. Кондитеры на BASIC получат разную выплату в зависимости от кодового пути. |

## 3. `POST /api/payment/create` (`src/app/api/payment/create/route.ts`)

**Что хорошо:** auth (JWT) + rate limit 5/min + проверка владения заказом + `isYookassaConfigured()` gate.

**Критично:**

| # | Проблема | Детали |
|---|----------|--------|
| 3.1 | 🔴 **Insert в `payments` с несуществующими колонками** | Пишет `user_id`, `gateway_response`, `gateway_txn_id`, `created_at` — в схеме (0002) есть только `yookassa_payment_id`, `amount`, `status`, `method`, `metadata`, `escrow_released_at`… Ошибка insert **не проверяется** (`await ...insert(...)` без `.error`) → **платёж молча не сохраняется** → webhook потом не найдёт запись → идемпотентность мертва. |
| 3.2 | 🔴 **Единицы (см. 2.2)** — `amount: Number(order.total)` как рубли. |
| 3.3 | 🟡 **Мёртвая проверка** | `payment_status === "paid"` — статуса `"paid"` не существует в enum `payment_status` (`pending/waiting_for_capture/succeeded/escrow/released/cancelled/refunded`). Двойная оплата не блокируется этой веткой. |

## 4. `POST /api/payment/webhook` (`src/app/api/payment/webhook/route.ts`)

**Что хорошо:** идемпотентный скип финальных статусов; `payment_status === "escrow"` guard; бонусы начисляются один раз (проверка `loyalty_transactions`); side-effects non-blocking; юнит-тесты (`route.test.ts`) + e2e-спека идемпотентности.

**Критично:**

| # | Проблема | Детали |
|---|----------|--------|
| 4.1 | 🔴 **Сумма и валюта из webhook не сверяются** | `object.amount.value` игнорируется: статус «succeeded» принимается как факт без сравнения с `order.total`/`payments.amount`. Подмена/частичная оплата/другая валюта не обнаруживаются. |
| 4.2 | 🔴 **Платёж ищется по последнему в заказе, а не по `object.id`** | `select ... order by created_at desc limit 1` + `update status` — при двух попытках оплаты статус пишется чужой попытке. `provider_payment_id` (`yookassa_payment_id`) должен быть ключевым. |
| 4.3 | 🔴 **CIDR-проверка IPv6 сломана, IPv4 неточна** | `ipInRange` не поддерживает IPv6: `baseParts.length !== 4` → всегда false → `2a02:5180::/32` **отклоняется всегда**. Маски `/27`, `/25` трактуются как «совпадение первых N октетов» = /24 (в 8 раз шире допустимого). Если YooKassa пришлёт webhook по IPv6 — платёж не подтвердится никогда. |
| 4.4 | 🟠 **Два обработчика webhook** | Next.js route **и** `supabase/functions/yookassa-webhook/index.ts` (edge, свой IP-allowlist `/24`, `verify_jwt=false`). Если зарегистрировать оба URL в ЛК YooKassa — side-effects (бонусы, письма, эскроу) сработают дважды; у edge-функции свои колонки и своя логика. |
| 4.5 | 🟠 **`payment.canceled` → `payment_status = "refunded"`** | Семантически неверно: отмена ≠ возврат (деньги не приходили). Ломает аналитику и последующие возвраты. |
| 4.6 | 🟠 **Идемпотентность «по статусу», не по событию** | Нет таблицы обработанных событий: конкурентные retry (YooKassa шлёт повторно при timeout) могут пройти между `select` и `update`. Нет `webhook_events(provider, event, object_id)` UNIQUE. |
| 4.7 | 🟡 **Нет PaymentLog** | Финансовые события пишутся только в `console.*`. |

## 5. `POST /api/payment/refund` (`src/app/api/payment/refund/route.ts`)

**Критично:**

| # | Проблема | Детали |
|---|----------|--------|
| 5.1 | 🔴 **Покупатель может сам себе вернуть деньги** | `if (!isAdmin && order.user_id !== user.id) → 403`, но **владелец заказа проходит** → refund создаётся → **сразу вызывается YooKassa refunds API** → деньги возвращаются. Нет проверки статуса заказа (DELIVERED → COMPLETED?), нет админ-апрува, нет холда. Это бизнес-логическая дыра: получил торт → вернул деньги. |
| 5.2 | 🔴 **Сумма возврата не ограничена** | Нет `amount <= payment.amount − refunded_amount`; частичные/повторные возвраты не контролируются. |
| 5.3 | 🔴 **Единицы** | `amount / 100` (копейки → рубли) — верно только для платежей, созданных через checkout. Для платежей из `/api/payment/create` (там amount в рублях) возврат будет в 100 раз меньше. |
| 5.4 | 🟠 **Зависит от несогласованных колонок** | Читает `payment.yookassa_payment_id` — у платежей из `payment/create` этого поля нет (они пишут `gateway_txn_id`, который не существует) → возврат молча не выполнится. |
| 5.5 | 🟡 **Fail-open при ошибке YooKassa** | Если `yookassaRes.ok === false` — refund остаётся `requested`, клиент получает 201 «успех». |

## 6. `PATCH/GET /api/orders/[id]` (`src/app/api/orders/[id]/route.ts`)

**Что хорошо:** 👏 **здесь уже есть настоящая машина состояний** `STATUS_TRANSITIONS` (PENDING→CONFIRMED→PREPARING→READY→IN_DELIVERY→DELIVERED→COMPLETED + ветки CANCELLED/REFUNDED) с ролевыми правами на каждый переход; владение заказом проверяется; таймстемпы статусов.

| # | Проблема | Детали |
|---|----------|--------|
| 6.1 | 🟠 **Нет optimistic lock** | `update ... eq("id")` без `eq("status", order.status)` — два конкурентных PATCH (курьер и админ) оба «успешны», второй молча перетирает. |
| 6.2 | 🟠 **Переходы не связаны с оплатой** | `PENDING → CONFIRMED` допустим при `payment_status = pending` (для предоплатной модели это ок, но правило не зафиксировано); `DELIVERED → COMPLETED` не учитывает эскроу. |
| 6.3 | 🟡 **GET доступен SUPPORT/COURIER целиком** | `payments(*)` в payload — курьер видит все платёжные данные заказа. |

## 7. `POST /api/orders/[id]/cancel` (`src/app/api/orders/[id]/cancel/route.ts`)

**Критично:**

| # | Проблема | Детали |
|---|----------|--------|
| 7.1 | 🔴 **`refundPayment(orderId, ...)` — передаётся orderId вместо paymentId** | Сигнатура: `refundPayment(paymentId, amount, description)`. Реальный возврат через YooKassa **не может сработать** (paymentId = UUID заказа). В mock-режиме — «успех». |
| 7.2 | 🔴 **`payment_status = "refunded"` ставится ДО факта возврата** | Если возврат упал (а он упадёт, см. 7.1), заказ помечен как возвращённый. Нет записи в `refunds`, нет ledger. |
| 7.3 | 🟠 **Race с escrow-release cron** | Заказ в `escrow` отменяется → cron в этот момент релизит → баланс кондитера увеличен, а деньги возвращены покупателю. Нужен атомарный переход `escrow → refunded` с блокировкой. |

## 8. Выплаты: `POST /api/payouts/request` + `GET/POST/PATCH /api/admin/payouts`

Три несогласованных контура:

**A. `/api/payouts/request` (самообслуживание кондитера):**
- 🔴 **Фильтр `payment_status = "succeeded"` — мёртвый**: ничего в коде не пишет статус `"succeeded"` (webhook пишет `escrow`, cron — `released`). Путь выплат не срабатывает никогда (или срабатывает на данных, созданных руками).
- 🔴 **Fallback не-атомарного списания**: при ошибке RPC `deduct_confectioner_balance` — `update balance: Math.max(0, balance - amount)` — race + `Math.max(0,…)` тихо прощает овердрафт.
- 🔴 **Частичная выплата помечает ВСЕ заказы выплаченными**: запросили 1 000 ₽ из 50 000 ₽ доступных → `payout_transferred_at` проставляется **всем** eligible-заказам → оставшиеся 49 000 ₽ выплатить невозможно.
- 🟠 **Не создаёт запись в `payout_requests`** → админ не видит выплату, reconciliation невозможен.
- 🟠 **Деньги реально не отправляются** (комментарий обещает YooKassa payout API — вызова нет). Тихо.
- ✅ Хорошее: 2FA (TOTP/backup), `checkConfectionerGate`, `verifyForPayout` (DaData), снапшот комиссии.

**B. `/api/admin/payouts` (payout_requests):**
- 🔴 **POST без проверки баланса и роли**: любой аутентифицированный пользователь может создать `payout_requests` на 10 000 000 ₽.
- 🟠 **approve не двигает деньги**: `status="approved"` — и всё. Нет вызова провайдера, нет списания, нет ledger. При этом инстансная выплата (контур A) вообще мимо этих записей.
- 🟡 approve идемпотентен случайно (повторный approve перезапишет `processed_by/at`).

**C. `/api/cron/escrow-release`:**
- ✅ `verifyCronSecret` (C6) — ок; optimistic lock `is("escrow_released_at", null)` — ок.
- 🔴 **Read-then-write баланса**: `select balance` → `update balance: newBalance` — два конкурентных релиза одному кондитеру = lost update (деньги потеряны). RPC `release_escrow` в миграциях отсутствует (есть только `release_escrow_after_delivery`, см. ниже).
- 🟠 **Дублирует формулы комиссии** (`DEFAULT_COMMISSION_RATE = 0.15`, `YOOKASSA_RATE = 0.025`) инлайн вместо `finance.ts calculateConfectionerPayout` (там ещё и налоги считаются — здесь игнорируются).
- 🟠 **Расчёт от `order.total`, не от платежа**: бонусы/промо уже в total — ок, но комиссия от `total − delivery` при смешанных единицах (2.1) даёт мусорные суммы.

**D. Мёртвый триггер:** `release_escrow_after_delivery` (миграция 0011) только пишет `release_scheduled_at` в `escrow_accounts` — **никто не обрабатывает** `release_scheduled_at`. Таблицы `escrow_accounts`/`split_payments` серверным кодом не наполняются (только «use-escrow.ts», см. ниже). Это имитация эскроу.

## 9. Библиотеки

- **`src/lib/yookassa.ts`** — детерминированные ключи, `isYookassaConfigured()`, mock-режим — хорошо. Слабости: `verifyWebhook` (4.3); mock возвращает `success: true` с `mock_` платежом (в dev ок, но `/api/payment/create` пропустит такой платёж в БД с несуществующими колонками); `amount: number` без указания единиц — **подпись функции провоцирует баг 100×**.
- **`src/lib/finance.ts`** — богатая библиотека (комиссии, НПД/УСН/ОСНО, `calculateConfectionerPayout`, эскроу-константы) — **но денежные пути её не используют** (каждый маршрут пересчитывает комиссию инлайн, со своими коэффициентами). `ESCROW.holdHours` не синхронизирован с `ESCROW_HOLD_HOURS = 24` в cron.
- **`src/lib/supabase/use-escrow.ts`** — 🔴 паттерн: клиентские React-хуки (`useQuery`/`toast`) **импортируют `supabaseAdmin`** (service role). Сейчас файл никем не импортирован (мёртвый) — но при первом же использовании service-role клиент попадает в клиентский бандл. Удалить/переписать.
- **`src/lib/loyalty.ts`** — образцовый модуль: атомарный RPC, double-spend guard, `calculateMaxRedeemable`. Его стоит взять как референс для платежей.

## 10. Схема данных: Prisma vs SQL (сильный дрейф)

| Сущность | Prisma (`prisma/schema.prisma`) | Реальный SQL (миграции) | Код API |
|---|---|---|---|
| Order | `customerId`, `total Int`, `paymentStatus` | `user_id` (NOT `customer_id`), **нет** `payment_status`, `tariff_snapshot`, `payout_transferred_at`, `escrow_released_at` в 0002 | webhook джойнит `customer_id`, checkout/orders пишут `user_id`, cron пишет `payout_transferred_at`, `payment_status` |
| Payment | `yookassaId`, нет `userId` | `yookassa_payment_id`, нет `user_id`/`gateway_txn_id`/`gateway_response` | payment/create пишет `gateway_txn_id`+`user_id`+`gateway_response` (не существует) |
| Confectioners | — | 0002-style (user_id snake) **и** 0017 `"confectioners"` c camelCase `"userId"` (вторая, несовместимая версия; попытка склейки — 0027) | `.eq("user_id", …)` |
| Ledger | **нет** | **нет** (только `escrow_accounts`, не используется) | — |

**Вывод:** Prisma-схема не является источником правды (рабочая БД — Supabase SQL). `Transaction`, `UserBalance`, `Ledger` — **не существуют нигде**.

# Часть III. Целевая production-архитектура

## 3.1. Принципы

1. **Единица денег — копейки, `INTEGER`, везде.** Конвертация в рубли — только на границе провайдера (`(kop/100).toFixed(2)`). Все функции денег принимают `*Kop` суффикс: `createPayment({ amountKop })` — компилятор не даст перепутать.
2. **Один источник истины по комиссиям** — `finance.ts calculateCommission/calculateConfectionerPayout` (ликвидировать локальные `TARIFF_RATES`/инлайн-формулы; привести BASIC к одному значению — бизнес-решение: 12% или 15%).
3. **Идемпотентность — уникальные ключи в БД**, а не проверки статусов: `payments.idempotency_key UNIQUE`, `webhook_events (provider, object_id, event) UNIQUE`, `ledger_transactions.idempotency_key UNIQUE`.
4. **Все денежные переходы — только через ledger** (двойная запись). Балансы — материализованное представление, обновляемое тем же RPC, что и записи.
5. **Webhook: verify → match by provider id → compare amount → ledger → side-effects.** Один обработчик; edge-функцию удалить/деактивировать.
6. **Выплаты — один пайплайн**: `payout_requests` (запрос+заморозка) → admin approve → провайдер → ledger. Никаких параллельных самообслуживаний мимо ledger.
7. **Тонкие контроллеры → `src/modules/`**: route.ts = auth + validate(Zod) + вызов service. Постепенно, начиная с payments.

## 3.2. Структура модулей

```

    state-machine.ts      # transitions + guard-и (единственная копия, миграция из orders/[id]/route.ts)
    policy.ts             # authorize(user, action, order) — ORDER_VIEW/ORDER_CANCEL/ORDER_TRANSITION
    schema.ts             # Zod: CreateOrderSchema, CheckoutSchema, CancelSchema

```

## 3.3. Жизненный цикл заказа v2 (машина состояний)

```
                    ┌────────────┐
                    │   DRAFT*   │  (*необязателен, cake-builder)
                    └─────┬──────┘
                          ▼
   ┌────────────►  ┌────────────┐   payment.create
   │  cancel       │  PENDING   │──────────────────┐
   │  (без оплаты) └─────┬──────┘                  ▼
   │                     │                 ┌───────────────┐
   │                     │ webhook         │ PAYMENT_SENT  │ (payments.status=pending)
   │                     │ payment.succeeded│      + amount==order.total
   │                     ▼                        │
   │               ┌────────────┐                 ▼
   │               │  CONFIRMED │  payment.canceled ──► CANCELLED (payment=cancelled)
   │               │  (escrow)  │
   │               └──┬──────┬──┘
   │     confectioner │      │ cancel после оплаты → REFUND_REQUESTED (админ-апрув)
   │                  ▼      ▼
   │            PREPARING  REFUND_*  (см. 3.6)
   │                  ▼
   │               READY ──► IN_DELIVERY ──► DELIVERED
   │                                            │
   │                        escrow-release cron │ (hold ≥ 24h, нет спора)
   │                                            ▼
   │                                       COMPLETED
   │                                            │  payout
   └────────────────────────────────────────────┘
```

Правила (код + optimistic lock в одном UPDATE):
- `transitionOrder(id, from, to, actor)` выполняет `update orders set status=$to where id=$id and status=$from` — 0 строк = гонка, вернуть 409.
- `PENDING → CONFIRMED` — только при `payments.status IN ('succeeded','waiting_for_capture')` ИЛИ `payment_method='cash'`.
- `DELIVERED → COMPLETED` — ручной (покупатель) или авто по таймеру 3 дня.
- Эскроу не завязан на `order.status`: он — следствие webhook (hold) и cron (release), статусные таймстемпы — только наблюдение.

```sql
-- ================================================================
-- Создание платежа: 1 попытка на заказ (идемпотентно)
-- ================================================================
CREATE OR REPLACE FUNCTION public.create_payment_atomic(
  p_order_id UUID, p_user_id UUID, p_amount_kop INTEGER, p_idempotency_key TEXT
) RETURNS UUID  -- payments.id
LANGUAGE plpgsql AS $$
DECLARE v_payment UUID; v_existing UUID;
BEGIN
  SELECT id INTO v_existing FROM public.payments
  WHERE idempotency_key = p_idempotency_key LIMIT 1;
  IF v_existing IS NOT NULL THEN RETURN v_existing; END IF;

  INSERT INTO public.payments (order_id, user_id, amount, status, idempotency_key)
  VALUES (p_order_id, p_user_id, p_amount_kop, 'pending', p_idempotency_key)
  RETURNING id INTO v_payment;

  INSERT INTO public.payment_attempts (order_id, payment_id, idempotency_key)
  VALUES (p_order_id, v_payment, p_idempotency_key);

  UPDATE public.orders SET payment_status = 'pending', updated_at = now()
  WHERE id = p_order_id;

  INSERT INTO public.payment_log (order_id, payment_id, event, actor, data)
  VALUES (p_order_id, v_payment, 'PAYMENT_CREATED', p_user_id::text,
          jsonb_build_object('amount_kop', p_amount_kop));
  RETURN v_payment;
END; $$;

-- ================================================================
-- Webhook payment.succeeded: verify+hold атомарно и идемпотентно
-- Вызывается ПОСЛЕ вставки webhook_events (dedupe по unique index)
-- ================================================================
CREATE OR REPLACE FUNCTION public.webhook_payment_succeeded(
  p_provider_payment_id TEXT, p_amount_kop INTEGER, p_order_id UUID
) RETURNS TEXT  -- 'processed' | 'duplicate' | 'amount_mismatch'
LANGUAGE plpgsql AS $$
DECLARE
  v_payment RECORD; v_order RECORD;
  v_platform UUID; v_escrow UUID; v_commission INTEGER; v_fee INTEGER; v_payout INTEGER;
  v_tx UUID;
BEGIN
  SELECT * INTO v_payment FROM public.payments
  WHERE provider='yookassa' AND yookassa_payment_id = p_provider_payment_id
  FOR UPDATE;
  IF NOT FOUND THEN RETURN 'unknown_payment'; END IF;
  IF v_payment.status_v2 = 'succeeded' THEN RETURN 'duplicate'; END IF;

  -- Сверка суммы: несоответствие = фрод-алерт, деньги не зачисляются
  IF p_amount_kop IS DISTINCT FROM v_payment.amount THEN
    INSERT INTO public.payment_log (order_id, payment_id, event, actor, data)
    VALUES (v_payment.order_id, v_payment.id, 'AMOUNT_MISMATCH', 'webhook',
            jsonb_build_object('expected', v_payment.amount, 'got', p_amount_kop));
    RETURN 'amount_mismatch';
  END IF;

  SELECT * INTO v_order FROM public.orders WHERE id = v_payment.order_id FOR UPDATE;

  UPDATE public.payments
  SET status_v2='succeeded', status='succeeded', updated_at=now()
  WHERE id = v_payment.id;

  -- Единая формула комиссии из finance.ts (снапшот в заказе)
  v_commission := round(
    (v_order.total - coalesce(v_order.delivery_cost,0)) * coalesce(v_order.commission_rate_snapshot, 0.15));
  v_fee := round(v_order.total * 0.025);
  v_payout := v_order.total - v_commission - v_fee;

  SELECT id INTO v_platform FROM ledger_accounts WHERE owner_type='PLATFORM' AND owner_id IS NULL;
  SELECT id INTO v_escrow   FROM ledger_accounts WHERE owner_type='ESCROW';

  -- Двойная запись: платёж пришёл → сразу в эскроу
  INSERT INTO ledger_transactions (idempotency_key, type, order_id, payment_id)
  VALUES ('payin:'||v_payment.id, 'PAYMENT_IN', v_order.id, v_payment.id)
  RETURNING id INTO v_tx;
  INSERT INTO ledger_entries (transaction_id, account_id, direction, amount_kop) VALUES
    (v_tx, v_platform, 'DEBIT',  v_order.total),
    (v_tx, v_escrow,   'CREDIT', v_order.total);

  INSERT INTO ledger_transactions (idempotency_key, type, order_id, payment_id)
  VALUES ('hold:'||v_payment.id, 'ESCROW_HOLD', v_order.id, v_payment.id)
  RETURNING id INTO v_tx;
  INSERT INTO ledger_entries (transaction_id, account_id, direction, amount_kop) VALUES
    (v_tx, v_escrow,   'DEBIT',  v_order.total),
    (v_tx, v_platform, 'CREDIT', v_commission + v_fee),   -- платформа: комиссия+fee
    -- кондитеру — на escrow-счёт (доступно будет после release)
    (SELECT id FROM ledger_accounts WHERE owner_type='CONFECTIONER' AND owner_id=v_order.confectioner_id AND kind='escrow'
      UNION ALL SELECT uuid_generate_v4()),   -- см. примечание: ensure_account ниже
    ...
  UPDATE public.orders SET payment_status='escrow', updated_at=now() WHERE id=v_order.id;

  INSERT INTO payment_log (order_id, payment_id, event, actor, data)
  VALUES (v_order.id, v_payment.id, 'PAYMENT_CONFIRMED', 'webhook',
          jsonb_build_object('commission', v_commission, 'fee', v_fee, 'payout', v_payout));
  RETURN 'processed';
END; $$;
```

> Примечание: для краткости в примере выше опущен helper `ensure_ledger_account(owner_type, owner_id, kind) RETURNS UUID` (INSERT … ON CONFLICT DO NOTHING RETURNING id) — в реальной миграции он обязателен и используется во всех RPC.

```sql
-- ================================================================
-- Релиз эскроу (cron): атомарно, без read-then-write
-- ================================================================
CREATE OR REPLACE FUNCTION public.release_escrow_atomic(p_order_id UUID)
RETURNS TEXT  -- 'released' | 'skipped'
LANGUAGE plpgsql AS $$
DECLARE v_order RECORD; v_seller_escrow UUID; v_seller_avail UUID; v_payout INTEGER; v_tx UUID;
BEGIN
  SELECT * INTO v_order FROM public.orders WHERE id = p_order_id FOR UPDATE;
  IF NOT FOUND OR v_order.payment_status <> 'escrow' OR v_order.escrow_released_at IS NOT NULL
     OR v_order.status = 'CANCELLED' THEN
    RETURN 'skipped';
  END IF;

  v_payout := v_order.total
            - round((v_order.total - coalesce(v_order.delivery_cost,0))
                    * coalesce(v_order.commission_rate_snapshot, 0.15))
            - round(v_order.total * 0.025);

  SELECT id INTO v_seller_escrow FROM ledger_accounts
  WHERE owner_type='CONFECTIONER' AND owner_id=v_order.confectioner_id AND kind='escrow' FOR UPDATE;
  SELECT id INTO v_seller_avail FROM ledger_accounts
  WHERE owner_type='CONFECTIONER' AND owner_id=v_order.confectioner_id AND kind='available' FOR UPDATE;

  -- escrow → seller.available + баланс платформы уже начислен при hold
  UPDATE ledger_accounts SET balance_kop = balance_kop - v_payout WHERE id = v_seller_escrow;
  UPDATE ledger_accounts SET balance_kop = balance_kop + v_payout WHERE id = v_seller_avail;

  INSERT INTO ledger_transactions (idempotency_key, type, order_id)
  VALUES ('release:'||p_order_id, 'ESCROW_RELEASE', p_order_id) RETURNING id INTO v_tx;
  INSERT INTO ledger_entries (transaction_id, account_id, direction, amount_kop) VALUES
    (v_tx, v_seller_escrow, 'DEBIT',  v_payout),
    (v_tx, v_seller_avail,  'CREDIT', v_payout);

  UPDATE public.orders
  SET payment_status='released', escrow_released_at=now(), updated_at=now()
  WHERE id = p_order_id;

  INSERT INTO payment_log (order_id, event, actor, data)
  VALUES (p_order_id, 'ESCROW_RELEASED', 'system', jsonb_build_object('payout_kop', v_payout));
  RETURN 'released';
END; $$;

-- ================================================================
-- Запрос выплаты: заморозка available → pending_payout, атомарно
-- ================================================================
CREATE OR REPLACE FUNCTION public.request_payout_atomic(
  p_confectioner_id UUID, p_amount_kop BIGINT, p_idempotency_key TEXT
) RETURNS UUID  -- payout_requests.id
LANGUAGE plpgsql AS $$
DECLARE v_req UUID; v_avail UUID; v_pend UUID; v_tx UUID; v_conf_user UUID;
BEGIN
  SELECT id INTO v_avail FROM ledger_accounts
  WHERE owner_type='CONFECTIONER' AND owner_id=p_confectioner_id AND kind='available' FOR UPDATE;
  SELECT id INTO v_pend FROM ledger_accounts
  WHERE owner_type='CONFECTIONER' AND owner_id=p_confectioner_id AND kind='pending_payout' FOR UPDATE;

  IF (SELECT balance_kop FROM ledger_accounts WHERE id=v_avail) < p_amount_kop THEN
    RAISE EXCEPTION 'INSUFFICIENT_FUNDS';
  END IF;

  UPDATE ledger_accounts SET balance_kop = balance_kop - p_amount_kop WHERE id = v_avail;
  UPDATE ledger_accounts SET balance_kop = balance_kop + p_amount_kop WHERE id = v_pend;

  INSERT INTO payout_requests (user_id, confectioner_id, amount, amount_kop, status, status_v2, idempotency_key)
  VALUES ((SELECT user_id FROM confectioners WHERE id=p_confectioner_id),
          p_confectioner_id, p_amount_kop/100, p_amount_kop, 'pending', 'pending', p_idempotency_key)
  RETURNING id INTO v_req;

  INSERT INTO ledger_transactions (idempotency_key, type, payout_id)
  VALUES ('payout-res:'||v_req, 'PAYOUT_RESERVED', v_req) RETURNING id INTO v_tx;
  INSERT INTO ledger_entries (transaction_id, account_id, direction, amount_kop) VALUES
    (v_tx, v_avail, 'DEBIT',  p_amount_kop),
    (v_tx, v_pend,  'CREDIT', p_amount_kop);
  RETURN v_req;
END; $$;
-- Аналогичные RPC: approve_payout → status_v2='approved';
-- mark_payout_paid(req, provider_payout_id) → pending_payout→PLATFORM debit, PAYOUT_SENT;
-- reject_payout(req) → pending_payout→available (PAYOUT_RETURNED).
```

**Единый расчёт выплаты (одна функция, без инлайн-копий):**

```ts
// src/modules/payments/ledger.service.ts
export function calcOrderSplit(order: {
  totalKop: number; deliveryKop: number; commissionRateSnapshot: number;
}) {
  const commissionKop = Math.round((order.totalKop - order.deliveryKop) * order.commissionRateSnapshot);
  const feeKop = Math.round(order.totalKop * YOOKASSA_FEE_RATE);
  const sellerPayoutKop = order.totalKop - commissionKop - feeKop;
  return { commissionKop, feeKop, sellerPayoutKop }; // инвариант: сумма = totalKop
}
```

## 3.6. Потоки, которые меняются

**Webhook (единственный обработчик, `src/app/api/payment/webhook`):**
```
1. verifyWebhook: корректный CIDR v4+v6 (библиотека ipaddr.js или таблица точных диапазонов),
   prod: отсутствие IP → 403. Dev: только NODE_ENV !== 'production'.
2. INSERT webhook_events … ON CONFLICT (provider,event,object_id,object_status) DO NOTHING
   → conflict ⇒ 200 {"idempotent": true}, обработка не повторяется.
3. SELECT payment WHERE yookassa_payment_id = object.id (fallback: metadata.orderId → order → active payment).
4. payment.succeeded → RPC webhook_payment_succeeded(provider_id, amountKop, orderId):
   не совпала сумма → фрод-алерт в payment_log, ответ 200 (YooKassa не ретраит вечно), деньги не зачислены.
5. Side-effects (бонусы, письма, telegram) — через outbox-таблицу, рассылку делает cron/n8n (не в транзакции webhook).
```

**Возврат:**
```
Покупатель:  POST /api/payment/refund  → refunds.status='requested' (деньги не двигаются)
Админ:       PATCH approve/reject (INSPECTOR не может approve — только смотреть)
approve → refund.service: refundPayment(providerPaymentId, amountKop, ключ 'refund:'+refund.id)
        → webhook refund.succeeded → RPC: ledger REFUND_OUT + payments.amount_refunded_kop += amount
        → order.payment_status='refunded' только здесь.
Лимиты: amount ≤ payments.amount − amount_refunded_kop; полный возврат только до COMPLETED.
```

**Выплата (один пайплайн):**
```
Кондитер: POST /api/payouts/request → 2FA + gates + RPC request_payout_atomic
          (available → pending_payout, payout_requests создан, виден админу)
Админ:    PATCH /api/admin/payouts {payoutId, action:'approve'}  → status='approved'
Система:  worker/cron picking approved → YooKassa Payouts API (Idempotence-Key 'payout:'+id)
          → mark_payout_paid → PAYOUT_SENT → payment_log. fail → reject_payout (возврат в available).
Всё, что не прошло через payout_requests, невозможно: удалить мгновенную выплату из payouts/request.
```

**Денежные инварианты (проверять ночным cron):**
```
SUM(ledger_entries DEBIT) = SUM(CREDIT) по каждой транзакции
payments.amount = commission + fee + seller_payout (per order)
ledger escrow-баланс платформы = SUM(orders где payment_status='escrow')
confectioners.balance ≈ ledger available (на период миграции; потом balance удалить)
```
