# DEVELOPMENT_ROADMAP.md

Приоритетный план разработки Conditera. Сформирован по результатам синхронизации 2026-11-16 (коммит `e7da599`). Приоритеты: P0 безопасность/данные → P1 основные сценарии → P2 функциональность → P3 UX/производительность.

Каждая задача: проблема → доказательство → решение → риск → тесты → критерий готовности → зависимость от Production.

## P0 — безопасность (можно начинать немедленно, независимо от Pi)

### P0-1. Устранить stored-XSS во входящих письмах
- **Проблема**: произвольный HTML от провайдера рендерится в админке без санитизации.
- **Доказательство**: `admin-email-tab.tsx:303` (`dangerouslySetInnerHTML`), источник `api/email/inbound/route.ts:69,92,102`.
- **Решение (минимальное)**: изолированный sandbox-iframe (`sandbox=""` + `srcDoc`) ИЛИ рендер text-версии; full-санитизация (isomorphic-dompurify) — вторая очередь.
- **Риски**: сломать легитимную вёрстку писем — мигрировать итеративно, оставить toggle «HTML/текст».
- **Тесты**: vitest-кейс с malicious-fixture (`<img onerror>`, `javascript:`-ссылки) — отсутствие обработчиков в DOM.
- **Готово**: malicious-fixture не исполняет обработчики; lint/typecheck чисто.
- **Зависимости от Production**: нет.

### P0-2. Публикация истории (по разрешению владельца)
- **Проблема**: 299 коммитов только в песочнице (R2).
- **Решение**: `git push origin main` ПОСЛЕ явного разрешения; перед push — `npm run check:full` + `ops:backup`.
- **Готово**: origin/main = локальному; Production-watch не показывает регрессий.
- **Зависимости**: разрешение владельца. Внутренне независимо от инцидента.

## P1 — критичные укрепления (независимо от Production)

### P1-1. Argon2id-миграция хэшей паролей
- **Доказательство**: `src/lib/auth.ts:128-140` bcryptjs; комментарии «Argon2id» ложные (`api/auth/login/route.ts:9`).
- **Решение**: `hashPassword` → Argon2id (@node-rs/argon2); `verifyPassword` — dual по префиксу (`$2b$`→bcrypt, `$argon2id$`→argon2); пере-хэш при успешном входе. Совместимо с GoTrue-only юзерами (у них нет `profiles.password_hash`).
- **Риски**: несовместимость старых хэшей — решается dual-verify; зависимости нативного модуля — проверить сборку Docker.
- **Тесты**: существующий auth-suite + новые векторы (roundtrip, legacy-hash verify, re-hash on login).
- **Готово**: новые пользователи — Argon2id; старые логинятся без сброса; комментарии соответствуют коду.
- **Зависимости**: нет (локальная БД есть).

### P1-2. Fail-closed blocked-check для мутирующих запросов
- **Доказательство**: `src/lib/auth.ts:293-296`.
- **Решение**: при ошибке чтения blocked-статуса — 503 для POST/PUT/PATCH/DELETE, warn+continue для GET.
- **Риски**: ложные 503 при кратких сбоях БД — допустимо (безопасность важнее).
- **Тесты**: мок ошибки БД → мутация 503, чтение 200.
- **Готово**: заблокированный/сбойный сценарий не пропускает мутации.
- **Зависимости**: нет.

### P1-3. Timing-safe сравнение X-Cron-Secret / X-N8N-Secret
- **Доказательство**: `src/lib/cron-auth.ts` (`!==`).
- **Решение**: `crypto.timingSafeEqual` с нормализацией длины (паттерн `proxy.ts:128-149`).
- **Тесты**: unit на совпадение/несовпадение/разные длины.
- **Готово**: все секретные сравнения — timing-safe.
- **Зависимости**: нет.

### P1-4. zod-валидация auth-роутов
- **Проблема**: ручная валидация без формата email/сложности пароля (`register/route.ts:134-152`); готовые схемы не подключены (`validation-schemas.ts`).
- **Решение**: применить `loginSchema`/`registerSchema` в auth-роутах (сохранить текущие коды ошибок/сообщения — обратная совместимость API).
- **Тесты**: расширить `route.test.ts` (51+ auth-кейсов) негативными форматами.
- **Готово**: невалидные входы отклоняются схемой; старые клиенты не ломаются.
- **Зависимости**: нет.

### P1-5. Восстановление Production (координация с Pi, не код)
- Регистрация на проде: деплой `cb42589+` после восстановления PostgREST/Caddy; проверить цепочку register→login→RLS. См. `PRODUCTION_COMPATIBILITY.md` §2.
- **Зависимости**: Pi/владелец.
